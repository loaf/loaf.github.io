从头开发AI Agent应用系列之八：增加搜索Agent，优化界面

loaf 2026-07-20 大约 18 分钟 技术 AI Agent 人工智能

工作流中调用Agent

1.与工具调用的区别

前面我们实现了受控的工具调用，这次是Agent。它们都是调用工具，但是区别在于：

维度 讨论，受控工具调用 搜索，受控 Agent
谁决定循环次数 开发者写死（MAX_TOOL_ROUNDS=3）的 for 循环 LLM 自主驱动（模型决定还要不要再搜）
循环载体 我们自己写的 for round in range(3) LangGraph create_react_agent 的图循环
充要条件 模型能调工具 LLM 自主驱动 ReAct 循环
工具集 固定 2 个（search_web / fetch_page） 固定 3 个（web_search / fetch_page / enough）

一次工具调用不构成 Agent。LLM 自主地"调工具 → 观察 → 再调工具 → 自己判断停没停"才构成 Agent（ReAct）。

注意 enough 工具是关键——它让模型自己声明"我搜够了"，这是 Agent 自主决策的落点。以前没有这种东西，是开发者到点强制收尾。

2.保证“受控”，Agnet的边界契约

Agent 不是黑盒乱跑。代码里给了硬边界：

边界 落点
工具集固定 create_react_agent(model, [web_search, fetch_page, enough]) 只挂这 3 个 @tool，模型不能发明新工具
循环上限固定 我们自己数 agent 节点次数，达 max_steps（默认 5）立即 break；不依赖异常停
IO schema 固定 输出 list[MaterialCard]（Pydantic），固定字段
失败兜底 未收敛 → 从累积搜索重建卡片 + partial=true（test_partial_on_no_converge 验）
可观测 每轮 on_step(thought/action/observation) 回调 → SSE agent_step 事件

这套边界保证：无论模型多"皮"，它都只能在节点内折腾，宏观拓扑不被它改写。这是"工作流优先，Agent 是例外"的技术体现。

3. LiteLLM 和 create_react_agent 间的对接

create_react_agent 要一个 LangChain ChatModel（要支持 bind_tools），但我们项目用 LiteLLM 调 LLM（要保证厂商无关抽象）。

两个世界怎么对接？

这里选择写一个适配器 LiteLLMChatModel(BaseChatModel)，内部调 litellm.acompletion，实现 bind_tools + _agenerate。

这样的话，Agent 既复用了和讨论/聊天同一个 LLM 调用路径（配置、key、重试都一致），又满足了 create_react_agent 对 ChatModel 接口的要求。

搜索后端：Tavily 优先 + DuckDuckGo 兜底

前面在演示中出现了报错，因为DuckDuckGo的搜索网络问题。

这里使用第三方的搜索工具，我选择了使用Tavily，因为我有一个API Key，大家可以自己去申请一下，每个月可以免费1000次搜索。以前是免费申请的，现在不知道情况怎么样。

现在是有API，走Tavily，没有，自动降级到DuckDuckGo Lite来搜索。

app/tools/search.py 的 web_search(query) 就是这个选择器。调用方（Agent 的 @tool）只看这个统一入口，不关心后端是谁。

无论哪条路径，返回结构统一成 {title, url, snippet, score}，失败一律返回空列表 []（不抛）——让 Agent 拿到"空结果"自行换关键词或收尾，而不是让 ReAct 循环崩掉。

代码

1. 适配器 app/workflow/nodes/collect/search_agent.py:LiteLLMChatModel

核心职责两件：

class LiteLLMChatModel(BaseChatModel):
    model: str = ""
    bound_tools_schema: list[dict] = Field(default_factory=list)

    def bind_tools(self, tools, **kw):
        # 把 langchain @tool 序列化成 OpenAI function schema, 存起来
        # (create_react_agent 启动时必调)
        self.bound_tools_schema = [convert_to_openai_tool(t) for t in tools]
        return self

    async def _agenerate(self, messages, ...):
        # litellm.acompletion(stream=False), 把返回归一化成 AIMessage
        # (含 tool_calls——用 langchain 标准 dict 结构, tools 节点据此执行工具)
        kw = self._build_kwargs(messages)
        response = await litellm.acompletion(**kw)
        msg = response.choices[0].message
        ...
        return ChatResult(generations=[ChatGeneration(message=ai)])

因为bind_tools 的默认实现会 raise NotImplementedError。所以必须自己实现 bind_tools，否则 create_react_agent(model, ...) 启动时直接挂。

BaseChatModel 是 pydantic 严格模型，在方法里 self.bound_tools = [...] 赋值会抛 ValueError: object has no field。得把 bound_tools 声明为字段（bound_tools: list = []）。

2. 工具集 search_agent._make_tools

用工厂函数（而非模块级 @tool），因为 enough 需要记录"搜了什么"：

def _make_tools(project_id, topic):
    state = {"searches": []}   # 闭包可变状态, partial 兜底用

    @tool
    async def web_search(query: str) -> str:
        """搜索查询词, 返回若干条结果。可多次调用、换关键词。"""
        results = await search_mod.web_search(query)
        state["searches"].append({"query": query, "results": results})  # 记下来
        ...序列化成文本...

    @tool
    async def fetch_page(url: str) -> str:
        """抓取一个 URL 的正文。"""
        return await fetch_mod.fetch_page(url)   # 复用 T-007b/T-006 实现

    @tool
    def enough() -> str:
        """声明"已收集足够", 收尾输出卡片列表。"""
        return "已收到'够了'信号。请输出最终资料卡片列表。"

    return [web_search, fetch_page, enough], state

fetch_page 是纯复用。

enough 工具没有真正的"副作用"，它只是个信号：模型调了它 = “我觉得够了”，于是接下来这一轮模型会直接在回复正文里给最终结果。

3. 主循环 search_agent.run_search_agent —— 受控 + 可观测

async def run_search_agent(topic, project_id, *, max_steps, on_step, model=None):
    chat_model = model or LiteLLMChatModel()           # 测试可注入 FakeModel
    tools, tool_state = _make_tools(project_id, topic)
    agent = create_react_agent(chat_model, tools, prompt=_AGENT_SYSTEM_PROMPT)

    agent_count = 0
    # ★ recursion_limit 给宽裕上限, 真正的停由 agent_count 计数硬控
    #   (避免依赖 recursion_limit 抛 GraphRecursionError 打断流)
    async for chunk in agent.astream(init, stream_mode="updates",
                                     config={"recursion_limit": (steps_cap+2)*2}):
        for node_name, update in chunk.items():
            if node_name == "agent":
                agent_count += 1
                # AIMessage 带 tool_calls → 推 thought+action 步骤
                # AIMessage 无 tool_calls → 是最终回答 (converged=True)
            elif node_name == "tools":
                # ToolMessage → 给上一个 action 步骤补 observation
            if agent_count >= steps_cap:               # ★ 受控硬停
                break

两个关键不变量：

  1. 一定返回（不卡死、不抛给上层）：max_steps 计数硬停 + partial 兜底重建卡片 + run_search_agent 内部全 try。SSE 层不用处理 GraphRecursionError。

  2. 不收敛也有东西给用户：_reconstruct_cards_from_searches 把累积的 web_search 观测原样变卡片（去重），标 partial=True。

落库走单一写入路径：每张卡片 store.save_material(source_type="search", relevance=...)，自动进 kb/pages/ + manifest。

4. SSE 桥接 app/api/materials.py:_stream_search

复用前面的 _stream_discussion 的 asyncio.Queue 桥（同步回调 ↔ 异步生成器），让 agent_step 事件按真实发生顺序实时流出（边搜边看）：

事件序列：

data: {"agent_step": {thought, action, action_input}}   ← Agent 决定调工具
data: {"agent_step": {observation, _observe:true}}      ← 工具返回结果
data: {"cards": [...], "partial": ..., "saved_ids":[...]}  ← 最终结果
data: [DONE]

5. API Key 钥匙串：key 怎么做到"不落盘"？

Python 侧 config.py 一行没改。key 的"存储位置"变了，但"读取方式"没变——还是从环境变量读。

链路是这样的：

flowchart TD
    A["前端“设置 API Key”页"]
    A -->|"invoke(set_secure_secret, ...)"| B["Rust keyring crate"]
    B -->|"写入"| C["系统钥匙串 (Windows Credential Manager / macOS Keychain)"]
    D["Rust 启动 sidecar 时"] -->|"读出"| C
    D -->|"注入环境变量"| E["Python sidecar<br>.env('DEEPSEEK_API_KEY', val)"]
    E -->|"读取"| F["config.py<br>从 os.environ 读 key（老路径，零改动）"]

全链路 key 不碰磁盘：keychain → Rust 内存 → sidecar env。.env 文件里不需要写 key，config.yaml 根本不存在。

关键代码（src-tauri/src/secret.rs + sidecar.rs）：

// secret.rs: 从钥匙串收集所有要注入的 key
pub fn collect_sidecar_envs() -> Vec<(&'static str, String)> {
    const KEYS_TO_INJECT: &[(&str, &str)] = &[
        ("DEEPSEEK_API_KEY", "DEEPSEEK_API_KEY"),
        ("TAVILY_API_KEY", "TAVILY_API_KEY"),
        ("OPENAI_API_KEY", "OPENAI_API_KEY"),
    ];
    // ...每个 get_secret, 有就收...
}

// sidecar.rs (dev): 注入到子进程环境
for (env_name, val) in crate::secret::collect_sidecar_envs() {
    cmd.env(env_name, val);
}

这样 Python 侧 Settings.deepseek_api_key 照常从环境变量读到值，但值来自钥匙串而非明文文件——既满足"不落盘"，又保持后端配置层简单。

为资料增加标签与删除功能

1. 后端模型 models/material.py —— 加 important 字段

class Material(BaseModel):
    ...
    important: bool = Field(default=False, description="是否标记为重要 (用户手动标)")

MaterialSummary（列表项）也加了同字段。两个模型都给 important 默认值，保证老数据兼容。

2. 后端 store kb/store.py —— 加 update_material

def update_material(project_id, material_id, *, title=None, snippet=None,
                    tags=None, important=None) -> Material | None:
    """按 id 更新资料的 manifest 字段 (部分更新)。返回更新后的 Material, 无则 None。"""
    mf = manifest.read_manifest(kb)
    entry = manifest.find_by_id(mf, material_id)
    if entry is None:
        return None
    # 部分更新: None 的字段保持原值
    if title is not None:    entry["title"] = title
    if snippet is not None:  entry["snippet"] = snippet
    if tags is not None:
        # 去重 + 保序 (用户标同一标签两次不应出现两条)
        seen = set()
        entry["tags"] = [t for t in tags if not (t in seen or seen.add(t))]
    if important is not None:
        entry["important"] = bool(important)
    manifest.write_manifest(kb, mf)   # 原子写
    return Material.model_validate(entry)

3. 后端 API api/materials.py —— 三个新端点

GET    /materials/{id}?project_id=   # 单条详情 (manifest + 正文)
PUT    /materials/{id}?project_id=   # 部分更新 (标签/重要/标题/摘要)
DELETE /materials/{id}?project_id=   # 删文件 + 删 manifest

project_id 走 Query 参数（不是 path）。因为同一个 material_id 在不同项目是不同资料（跨项目隔离），必须显式带 project_id。用 Query 而非 body 是因为 DELETE 习惯无 body、GET 也无 body，Query 最通用。

PUT 的请求体 MaterialUpdateRequest 全字段可选（部分更新）：

class MaterialUpdateRequest(BaseModel):
    title: str | None = None
    snippet: str | None = None
    tags: list[str] | None = None
    important: bool | None = None

store.delete_material 没命中返回 False，API 层包成 {deleted: false}，不报 404。

4. 前端 api/client.ts —— 三个新函数 + important 字段

export interface Material {
  ...
  important: boolean;   
}

export async function getMaterial(projectId, materialId): Promise<MaterialDetail>
export async function updateMaterial(projectId, materialId, patch): Promise<Material>
export async function deleteMaterial(projectId, materialId): Promise<{deleted, material_id}>

updateMaterial 的 patch: MaterialUpdate 全字段可选，和后端的部分更新语义对齐。
