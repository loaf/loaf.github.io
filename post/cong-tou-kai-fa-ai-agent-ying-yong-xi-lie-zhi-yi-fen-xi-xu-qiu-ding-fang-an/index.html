从头开发AI Agent应用系列之一：分析需求定方案

loaf 2026-07-13 大约 10 分钟 技术 Agent LLM AI

本系列会从头开始，手把手教你开发一个AI Agent应用。经过本系列文章的学习，我们就应该可以开发一个完整的桌面版智能体应用。

之一：分析需求，制定好开发方案

本文先从智能体的基础概念说起，以确定好流程框架、开发技术栈结束。许多内容仅为个人理解，未必正确。

一、预备知识/概念

智能体到底是什么？

抛开概念，简单来说，业务流程中有很多节点需要人工判断，人工操作。其中有部分节点是可以用AI来替代的。智能体就是做这些工作的。

你需要开发一个程序，这个程序运行的仍是日常的工作流，但是后台有许多节点原来是需要你打电话、查表格来进行处理，现在这些烦琐易错的工作让大模型来给你处理了。

和传统应用相比，你的程序有头脑（大模型）、有手有脚（用CLI、MCP），有耐心懂规矩（用Loop、Harness）、会反思能总结（用Skill、Memory）。

从宽泛的定义来看，这个应用程序就是一个AI智能体。

从严格一点的定义来看，应用程序中只有涉及到调用大模型的部分才是智能体。但这里的调用并不是简单地输入提示词，等待大模型的回复这么简单。因为在一次简单的调用中，会涉及到很多具体的逻辑，比如动态路由、循环、失败重试等。所以：智能体=大模型+控制

智能体框架

很明显，不同的业务场景肯定有不同的大模型控制方法。框架就是这些控制方法的总结，它将通用大模型转化为具备环境感知、任务拆解和自主决策的具体能力。

下面是常用的3种框架。

1）LangGraph 基于图的控制流

LangGraph框架将智能体逻辑视为一个“图”（Graph）。适合需要精细控制状态机和复杂循环逻辑的Agent，能处理任务失败回溯、状态持久化等复杂场景。

在完成一次大模型调用时，从输入提示词开始，LangGraph将执行过程理解成一个个节点，每个节点是一个状态，这些状态是有序的。这些有序关系将节点连成一个图状结构。

上面是一个节点单纯但控制复杂的示意图，在输入要求后，调用一个路由功能，开三个代理并行工作，其中研究员代理节点涉及到多次循环，然后将三个代理的工作成果汇总生成报告进行审核。

从上面能看出，控制的流程可以非常复杂，而且每个状态都是checkpoint状态点，可以回顾审查当时的状态。控制流程如果简化的话，可以从图状变成线型。从二维变成一维，那么这个框架就是LangChain了。

2）AutoGen 基于对话式多智能体循环

AutoGen框架由微软开源，专注于“群体智能”，通过智能体间的对话驱动任务流转。易于创建不同角色的智能体（如程序员、测试员），并支持“人在回路”。

也就是说，这个框架更适合于多个角色讨论后，再通过类似于投票机制，或者仲裁角色的方式选择下一步的流转方向。工作流未必是固定的。而是在对话中涌现出来的。

3）CrewAI 基于角色的团队协作

CrewAI框架强调“工作流”和“协作逻辑”，为智能体引入“职位”、“任务”等概念，逻辑接近真实团队管理，可设定“经理”角色进行监督。

好比一家公司里领导安排你的事务性工作，如市场调研、内容创作、金融分析等。CrewAI适用于任务边界清晰、流程相对固定的自动化工作流。

二、需求分析

让我们从需求开始

先明白自己到底要写什么。这里我们以一个智能写作平台为例。

主要流程很简单：收集资料 → 生成初稿 → 人工定稿 → 多平台发布

先尽可能详细地构想每一步的功能，就每个功能进行头脑风暴，然后再大幅度地消减功能，精减流程。一放一收之间优化设计。

因为需要分析不是我们的重点，回到本教程，我们选择一个容易实现、功能明确的方案为模板。将上面的步骤分别画流程图

① 资料收集

通过多种方式，最终形成一个资料库。

graph LR
  A1[确定主题] --> A2[网络搜索]
  A2 --> A21[选中内容]
  A1 --> A3[AI 讨论]
  A3 --> A4[自动总结]
  A1 --> A51[选择文件]
  A51 --> A5[手动导入]
  A21 & A4 & A5 --> KB[(资料库)]

② 生成通稿

在资料库限定的范围内，根据用户要求，生成一个通用的初稿

graph LR
KBformS1[(资料库)] --> B1[[AI 生成]]
B2[用户要求<br/>主题/风格/大纲/要点] --> B1
B1 --> B3[初稿文本 <br>+<br> 配图]
B3 --> B4{人工审稿}
B4 -- 修改 --> B1
B4 -- 通过 --> DRAFT[(通用初稿)]

③ 定稿 & 发布

在通稿的基础上，生成多种不同格式的发布用稿。然后适配不同的工具，一键发布。

graph LR

        DRAFTformS2[(通用初稿)] --> C1[[AI 格式适配]]
        C2[平台要求<br/>公众号/小红书/抖音] --> C1
        C1 --> C3{人工审稿排版}
        C3 -- 修改 --> C1
        C3 -- 通过 --> C4[(专稿定稿)]
        C4 --> C5[[一键发布]]

纠结的选择

面对上面的工作流程，我们需要的是引入AI实现自动化。

所以从直观上，我们应该使用工作流，但是在某一个节点，当AI加入后，又想利用AI的主动性，比如Hermes能实现的功能，AI自己会调用多个工具，相当于自动改造了工作流，在图中增加更多的控制点。

这样的话，在实现开发中，我们就会面临两个选择：

方案一是，用符合常规思路的工作流，某些节点调用AI智能体。

方案二是，改造工作流，将AI智能体中的一些功能（比如多代理检索、并行分析等）直接写到工作流中。

选择方案一，找一个开源的Agent进行二次开发，将这个Agent当作一个AI节点嵌入工作流中。

选择方案二，需要直接理解各种Agent软件的优缺点，然后参考原理、精减代码，根据自己的实际需要增加工作流节点。然后在节点实现Agent的Skills、MCP、Harness和Loop。相当于将现在常用的智能体拆开自己拼装一个。

定义一个原则

上面的纠结可以简化为一个选择：

每一段控制流,到底应该由谁来决定?是由开发者预先写死,还是由模型在运行时生成?

在Anthropic 那篇 Building Effective Agents 里有一个我觉得很对的工程判断:优先用工作流,只有当任务的控制流在根本上无法预先枚举时,才用 Agent。

原因很简单：工作流可调试、可预测，控制流明确，反馈直观。我们不能把AI的自主性当作目的，而应该认识到它只是一个手段，只有在“不交给它就没法做”时才值得去选。

现在我们再来分析上面的两个方案。

方案一，嵌入一个现成的Agent当作节点，首先，我们提到的主流Agent框架是接管整个任务，而不是当作节点来用，先天有冲突。其次，如果这么做了，这个节点就成了黑盒，如果这个黑盒节点中有8步，第5步错了，你根本不知道是怎么回事。

方案二，相当于在业务中重写了现有各类Agent，与AI相关的功能只剩下了API调用。好处是，写一遍你就理解了更多的细节，可以自己写一个龙虾之类的智能体了。工程量大还是小事，主要是效果可能会变差。将原来让LLM凭语义可以决定的东西，硬编码成确定性逻辑了。

比如说，上面的资料收集中的“搜索网络”，如果交给LLM，它会智能判断，如果你的主题是编程类的，它会自动搜索github、CSDN等网站，如果是金融类，它会自动搜索金融街、雪球等网站。而你一定要将这类LLM可以凭语义决定的逻辑硬编码，代码冗长的同时灵活性反而下降。而且还可能出现资源浪费，比如我们可能会为了提高效率，同时激发多个Agent并行，但是同一个流程节点在处理不同任务时，需要的资源可能有天壤之别。

很明显，方案二先被淘汰，因为它根本没有“智能”。

只能选择方案一了。就是主要流程由自己控制，别让AI跨节点地改造你的工作流拓扑。这个工作流才是你的业务核心。

那么怎么解决方案一的缺陷呢？

每个节点首先不能是直接调用Hermes、OpenClaw之类的工具，也不能是某个框架，比如CrewAI、NanoBot之类，即使某些具体节点看起来很适合某种特定框架或者工具也不能直接调用。这个能不能调用的标准在于是否可控。

这样的话，我们应该做的是在特定需要AI参与的节点，写自己的Agent，这个Agent是轻量的。在这个节点的边界内实现ReAct循环，调用多个工具。（关于ReAct，可以参看前面的文章https://mp.weixin.qq.com/s/pGBvAHvf0owmhEFxqF1-7Q ）

这样我们可以确定智能体开发的原则了：

  1. 先设计确定性工作流主干,明确每个节点的输入输出。
  2. 对每个节点,判断它"需不需要 AI"以及"控制流能不能预先写死":
    • 不需要 AI → 普通函数节点。
    • 需要 AI 但控制流可写死 → LLM 单次调用(或 prompt chaining 等工作流模式)。
    • 需要 AI 且控制流不能写死 → 受控 Agent。
  3. 对于受控 Agent 节点,不手搓 ReAct 实现,而是用成熟库的能力(LangGraph 的 create_react_agent),自己只定义边界契约:工具集固定、循环上限、输入输出 schema、退出条件、可中断、可观测。
  4. Agent 的"自主"永远只在节点内部发生,不污染宏观工作流拓扑。

有原则有需求，自然就能出方案

根据需求定框架

根据需求，我们的的项目主干是三个流程的简单顺序串联。而每个流程里又各有一个子图，子图内再按节点进行拆分。

用LangGraph StateGraph作为主干是再恰当不过了。

为什么不选CrewAI呢？首先，与我们的节点内使用轻量ReAct循环违背。其次，CrewAI的设计哲学是“一次性完成”。它给每个Agent分配Task，任务完成后输出结果，流程就结束了。而上面的流程明显看到，步骤之间的多次循环，比如人工定稿时会有返回原节点的循环。

根据原则定方案

首先，我们看一下哪些节点可能需要用到AI：

流程① 资料收集

节点 是否需要AI 流程是否写死 说明
确定主题 否 是 表单输入，输出topic字符串
网络搜索 是，受控Agent 否，根据搜索结果决定 表单输入，输出topic字符串
AI讨论 是，对话式Agent 否，对话轮数动态 边界契约，topic进，讨论记录出
AI自动总结 是 是 固定prompt单次总结讨论记录
手工导入文件 否 是 文件目录

流程② 生成通稿

节点 是否需要AI 流程是否写死 说明
选择资料 否 是 选择资料
用户要求 否 是 输入文本要求
AI生成 是 是 LangGraph中prompt chaining,控制可写死，输出初稿
人工审稿 否 是 人工处理，需要时让才让AI再次生成

流程③ 定稿 & 发布

节点 是否需要AI 流程是否写死 说明
输入平台要求 否 是 输入提示词
AI格式适配 是 是 prompt chaining,单次调用
人工审稿 否 是 人工处理，根据需要让AI重写或直接在此基础上修改
一键发布 否 是 平台API调用

列出后很容易发现，此项目中要用的AI的地方并不多。完全不需要直接使用引入完整的第三方Agent，只要使用ReAct即可。

其次，决定技术栈：

  • 前端，选择Node.js+Vite
  • 后端，选择FastAPI（Python 3.12）
  • Shell，选择Tauri
  • LLM抽象层，选择LiteLLM
  • 富文本编辑器，选择Tiptap
  • 数据库，选择SQLite（保存元数据及工作流状态）
  • 网络搜索，选择TavilyAPI
  • 文生图，调用通义万相
