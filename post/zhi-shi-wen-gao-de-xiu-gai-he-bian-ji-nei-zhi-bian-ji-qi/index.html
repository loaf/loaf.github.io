从头开发AI Agent应用系列之十：文稿的后续处理

loaf 2026-07-20 大约 18 分钟 技术 LLM AI Agent

之十：文稿的修改和编辑，内置编辑器

现在基本流程都已经完成，但是还有最后一块拼图没有完成。那就是对生成的文稿的处理，这里使用Tiptap富文本编辑器，考虑到主要格式是markdown，这里使用其社区库tiptap-markdown扩展。

为了优化体验，在文稿编辑中还增加了选中文字的改写、生图、润色等AI功能。

最后增加一个版本快照与回退的功能。

到此，这个应用能的主干功能就已经完成。

嵌入TipTap编辑器

步骤 1：安装依赖

Tiptap 是模块化的，按需装：

cd src
npm install @tiptap/react @tiptap/pm @tiptap/starter-kit @tiptap/extension-image tiptap-markdown
包 作用
@tiptap/react React 绑定（useEditor / EditorContent）
@tiptap/pm ProseMirror 核心依赖（peer）
@tiptap/starter-kit 开箱即用的节点/标记集合（标题/段落/引用/代码块/列表/粗体斜体/水平线/链接…）
@tiptap/extension-image 图片节点（![alt](url)）
tiptap-markdown ★ markdown 存储路径核心——让 Tiptap 读写 markdown 字符串

版本对齐：装出来是 Tiptap v3.29.2。tiptap-markdown@0.9.0 的 peerDep 是
@tiptap/core: ^3.0.1，与 v3 对齐（早期 v0.8.x 是给 v2 用的，别装错）。

步骤 2：新建 src/src/components/editor/ 目录

三个文件：

src/src/components/editor/
├── MarkdownEditor.tsx   # Tiptap 编辑器本体（useEditor + EditorContent）
├── Toolbar.tsx          # 格式化工具栏
└── editor.css           # .tiptap-prose 排版样式

步骤 3：MarkdownEditor.tsx —— 核心组件

前面用textarea占位，现在用Tiptap替换：

核心 30 行：

import { useEffect } from "react";
import { useEditor, EditorContent } from "@tiptap/react";
import StarterKit from "@tiptap/starter-kit";
import Image from "@tiptap/extension-image";
import { Markdown } from "tiptap-markdown";
import "./editor.css";
import Toolbar from "./Toolbar";

export default function MarkdownEditor({ initialMarkdown, onChange }: Props) {
  const editor = useEditor({
    extensions: [
      StarterKit,
      Image,
      Markdown.configure({ breaks: true, html: false }),  // ★ markdown 存储
    ],
    content: initialMarkdown,                             // 进：初始 markdown
    editorProps: { attributes: { class: "tiptap-prose", spellcheck: "false" } },
    onUpdate: ({ editor }) => {                           // 出：变化 → markdown 回调
      const md = (editor.storage as { markdown?: { getMarkdown: () => string } })
        .markdown;
      onChange(md ? md.getMarkdown() : "");
    },
  });

  // 草稿切换重载（emitUpdate:false 避免误触发 dirty）
  useEffect(() => {
    if (editor) editor.commands.setContent(initialMarkdown, { emitUpdate: false });
  }, [initialMarkdown]);

  useEffect(() => () => editor?.destroy(), [editor]);    // 卸载销毁

  if (!editor) return <div>编辑器初始化…</div>;          // useEditor 首帧 null
  return (
    <div style={{ display: "flex", flexDirection: "column", flex: 1, minHeight: 0 }}>
      <Toolbar editor={editor} />
      <div style={{ flex: 1, overflowY: "auto", minHeight: 0 }}>
        <EditorContent editor={editor} />
      </div>
    </div>
  );
}

步骤 4：改 DraftEditor.tsx —— 替换 textarea

原文件是标题输入 + <textarea> + 保存。改动：

  • content 状态从 string 改为 string | null（null 表"未加载"，避免空串初始化闪屏）。
  • <textarea> 换成 <MarkdownEditor key={draftId} initialMarkdown={content} onChange={handleEditorChange} />。
  • handleEditorChange(markdown) 接收编辑器抛出的 markdown，更新 state + 标 dirty。
  • 标题输入框、保存按钮、dirty 提示、保存状态条全部保留不变（验收明确要求）。
  • 保存逻辑 updateDraft({ title, content }) 零改动——content 还是 markdown 字符串。

用AI实现部分改写

我们在编辑器里修改文章自然是没有什么问题的，但是既然用到了AI，我们当然会要求更多。

现在能想到的是：选中一段文字，然后让AI对这段文字进行改写、缩写、扩写。

后端

步骤 1：prompt 模板（app/llm/prompts/rewrite_*.md，4 个文件）

每个模板结构一致：角色定位 → 6 条要求（只输出文本/保持 markdown 格式/保持原意或按 action
调整篇幅/不编造/不改事实数据）→ {selection} 占位符。restyle 多一个 {style_hint}。

步骤 2：改写主逻辑（app/draft/rewrite.py，新建）

镜像 generator.py 但更简单：

  • RewriteAction = Literal[...] —— Pydantic 用它校验 action（非法值 422）。
  • build_rewrite_messages(selection, action, style_hint) —— 选模板、填占位符、返回单条 user。
  • stream_rewrite(...) —— 透传 llm.chat，和 stream_generate_draft 同构。

步骤 3：API 端点（app/api/editor.py，新建）

镜像 drafts.py：

  • RewriteRequest 模型（action/selection/style_hint）。
  • _require_draft 守卫：项目存在 + 草稿归属 → 404（防越权改写别人文稿）。
  • _stream_rewrite —— SSE 流（{chunk}/{error}/[DONE]）。
  • rewrite_draft 路由 —— 入流前预校验输入（422），再开流式。

步骤 4：注册 router（main.py 加 app.include_router(editor.router)）

前端

步骤 5：API 客户端（client.ts 加 streamRewriteDraft）

复刻 streamGenerateDraft 的 fetch + ReadableStream + SSE 解析模式（EventSource 不支持 POST）：

export async function streamRewriteDraft(
  projectId, draftId, selection, action, onChunk, styleHint?
): Promise<void> {
  const res = await fetch(`${base}/api/v1/drafts/${draftId}/rewrite?project_id=${projectId}`, {
    method: "POST",
    body: JSON.stringify({ action, selection, style_hint: styleHint ?? null }),
  });
  // ...读 SSE 流, data.chunk → onChunk, data.error → throw, [DONE] → return
}

步骤 6：改写面板（components/editor/RewritePanel.tsx，新建）

三态组件：

  • idle：监听 editor.on('selectionUpdate')，有非空选区时显示浮动 action 工具条
    （用 window.getSelection().getRangeAt(0).getBoundingClientRect() 定位）。
  • loading：点 action 后，调 streamRewriteDraft，边收边渲染新文本。
  • done：流结束，算 diff，显示红删绿增 + 采纳/放弃。

采纳用 Tiptap 命令替换选区：

editor.chain().focus()
  .deleteRange({ from, to })   // 删选中
  .insertContent(newText)      // 插新文本
  .run();                       // 提交事务 → 触发 onUpdate → 标 dirty

步骤 7：接入编辑器（MarkdownEditor.tsx 渲染 <RewritePanel>）

MarkdownEditor 加 projectId/draftId 两个 props（透传给 RewritePanel 调改写端点），DraftEditor 传进来。

AI生图

在编辑器中选中文字，然后根据这些文字调用工具AI生图：

[!TIP]
生图图片持久化进资料库（kb/images/），编辑器引用稳定 URL（/materials/{id}/image）， 不引用文生图 API 返回的临时签名 URL（那个几分钟就过期，图会丢）。

后端

步骤 1：config（config.py 加 image_api_key/image_api_base/image_model/image_size

  • has_image_key 属性；.env.example 加注释模板）

步骤 2：LLM 路由（router.py 加 generate_image(prompt) -> bytes）

用 litellm.aimage_generation(model=..., prompt=..., response_format="b64_json", ...)。

优先取 b64（直接 decode 成 bytes），兜底 URL（urllib 下载成 bytes）。统一返回 bytes 让editor.py 存进资料库。

步骤 3：prompt 模板（image_gen.md）

image_gen.md：把选中段落转成英文画面提示词（要求画面化、加风格关键词、no text）。

步骤 4：业务逻辑（app/draft/image_gen.py）

image_gen.py：build_image_prompt_messages（选中文本进 prompt）→ derive_image_prompt
（攒齐流式 chunk 成完整提示词）→ generate_image_for_selection（两步链路，返回 (prompt, bytes)）。

步骤 5：端点（editor.py 加 generate-image ）

POST /drafts/{id}/generate-image：SSE 推 {status}×2 → {image} → [DONE]。图片存 kb/images/ 返回稳定 URL。

前端

步骤 6：API 客户端（client.ts 加 generateImage + streamPolishDraft + GeneratedImage 类型）

generateImage：复刻 SSE 消费模式，{status} → onStatus，{image} → onImage，{error} → throw。

步骤 7：RewritePanel 扩展（加 image action 分支）

  • TOOL_ACTIONS 加 image（浮动工具条多一个 🖼生图 按钮）。
  • handleGenerateImage：调 generateImage，拿到图直接 editor.setImage() 插入（无 diff）。
  • 渲染分支：image 走图片预览面板。

全文润色

初稿写完，想整体过一遍（修错别字、理顺句子、删冗余）——但"选中改写"是 逐段的，全文润色得手动选完整篇。这里可以一键润色，diff 展示改了哪些， 确认后应用。

[!TIP]
润色不落库（和改写一致）—— 只产出润色后文本，采纳才调既有 PUT /drafts/{id}。

这个功能和上面的生图流程基本一致。只是在下面的细节上有点差异：

后端

在步骤 3：prompt 模板（ polish.md）

polish.md：全文润色（修错别字/语病/用词/衔接，不改结构不改原意，保篇幅）。

在步骤 4：业务逻辑（app/draft/polish.py）

polish.py：build_polish_messages（整篇进 prompt）→ stream_polish（透传 llm.chat， 和 stream_rewrite 同构）。

在步骤 5：端点（editor.py 加polish）

POST /drafts/{id}/polish：SSE 推 {chunk}×N → [DONE]。取 db.get_draft(draft_id)["content"] 作输入，空内容 → 422。

前端

在步骤 6：API 客户端（client.ts 加 streamPolishDraft 类型）

streamPolishDraft：和 streamRewriteDraft 同构（{chunk} → onChunk）。

在步骤 7：RewritePanel 扩展（加 polish action 分支）

  • handlePolish：调 streamPolishDraft，攒齐走 diff，采纳 selectAll + 替换。
  • registerPolish prop：把 handlePolish 注册给父组件。
  • 渲染分支：polish 走 diff 面板（复用改写的 diff UI）。

在步骤 8：Toolbar + MarkdownEditor 接线

  • Toolbar 加 onPolish prop + 「✨ 润色」按钮（分隔线隔开，紫色强调区分 AI 工具）。
  • MarkdownEditor 持 polishFn state，registerPolish 时 setPolishFn，传给 Toolbar 的 onPolish。

增加版本历史

这个功能其实是一个习惯性功能，反正大多数的编辑器都有这个功能，就加上呗。

设计的流程为：


两个关键设计：

  • 自动快照存的是"旧 content"（保存前的状态），不是新 content——因为新 content 已经
    落进 drafts，旧 content 这一刻就丢了，必须此刻抓住。回退目标 = “保存前的样子”。
  • 回退前给当前内容也存快照——回退也是改动，回退前状态值得留版本（万一回退错了能再回退）。

后端

步骤 1：db 层（db.py 加 draft_versions 表 + 4 个函数）

  • _SCHEMA 追加 draft_versions CREATE（含 FK CASCADE + 索引）。
  • create_draft_version(draft_id, content, *, label) — 存快照，返回 version_id。
  • list_draft_versions(draft_id) — 列表（不含 content，倒序）。
  • get_draft_version(version_id) — 详情（含 content）。
  • delete_draft_version(version_id) — 删单条（预留）。

步骤 2：自动快照钩（drafts.py 的 update_draft）

PUT 保存时，content 变化 → db.create_draft_version(draft_id, existing["content"]) 存旧内容。一行代码，在 update_draft 之前。

步骤 3：版本端点（editor.py 加 4 个路由）

  • GET /drafts/{id}/versions — 列表（VersionResponse，不含 content）。
  • POST /drafts/{id}/versions — 手动快照（带 label，返回详情含 content）。
  • GET /drafts/{id}/versions/{vid} — 详情（预览用）。
  • POST /drafts/{id}/rollback/{vid} — 回退（存当前快照 + 写回目标 content）。

全部复用 _require_draft 守卫。版本归属也校验（target["draft_id"] != draft_id → 404，防越权回退别的草稿的版本）。

前端

步骤 4：API 客户端（client.ts 加 4 个函数 + 2 个类型）

DraftVersion（列表项，无 content）、DraftVersionDetail（详情，有 content）。

listVersions/getVersion/createVersion/rollbackVersion，复刻 getDraft/updateDraft的 apiGet/apiSend + project_id query param 模式。

步骤 5：版本面板（components/editor/VersionPanel.tsx，新建）

侧边抽屉式：顶部「📌 打快照」按钮 → 时间线（label + 时间，倒序）→ 选中后底部预览区（markdown 原文）+ 「↩ 回退到此版本」按钮。回退有 confirm 确认（防误操作）。

步骤 6：接入 DraftEditor（顶栏加「🕐 历史」按钮 + 布局改并排）

  • 顶栏加「🕐 历史」按钮（toggle 版本面板开关）。
  • 布局从"编辑器占满"改成"编辑器 flex:1 + 版本面板 300px 并排"（面板收起时不渲染）。
  • 回调 onRolledBack：setContent + setReloadKey + 标 dirty。

最后的反思

到这里，基本的功能都已经实现。我把代码全部上传到githhub上，（github.com/loaf/mewgo-study）可以将源代码在本地编译运行，有兴趣的朋友可以试一试。

这个项目中大多数内容都是用AI生成。我是用ZCode+GLM5.2来完成的。效果很好。原来我的主力应用是OpenCode+DeepSeek，平时也用OpenClaw和Hermes，写代码都用Tare+GPT，但这段时间用ZCode后感觉越用越顺手了。

我认为原因主要在于Zcode。其实模型的差异可能比我们想象的要小的多，但是好用不好用，关键在于对模型的控制。

好比这个已经完成的文稿生成器，其实一分解，就明白调用AI的部分很简单，但是为什么都是调用别人的大模型，别人写的产品就非常好呢？关键就在于控制。这也是为什么大模型开发需要经验的地方，这也是Harness工程如此重要的原因。当然，现在主流的概念又从Loop转到了Graph。但本质相同，对于调用过程的控制和使用才是AI工程师的核心竞争力。这个其实就是经验了。

写到系列十，也应该结尾了。本来还计划写多平台自动发布，想加上一键部署到指定平台什么的，但发现大家并不太喜欢这个系列也没有兴趣继续写了，只能草草收尾。

应用也只能算是半成品，非常粗糙。比如界面的简陋，功能也有很多问题。比如AI改写吧。我是直接将选中的文字丢进AI，其实还应该将当前文章的风格、语气、内容等也细化分类总结，然后拼成控制prompt投入才对。

而且还有一个很大的问题值得我反思：

技术架构中选择了LangGraph是否有必要？

因为我发现，节点的回退等应用场景并不存在。

LangGraph 在项目里 app/workflow/graph.py 的四阶段状态机 + checkpoint + interrupt/resume，在项目中几乎都没有用上。只在 app/workflow/nodes/collect/search_agent.py里使用create_react_agent 预构建 ReAct Agent。

项目中没有条件路由、没有回退、跳转和分支，也没有并行节点。

这么看来，把LangGraph架构全部删除也不影响代码的运行。只是已经写了一大半，也懒得再动地基了。
