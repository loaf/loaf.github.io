从头开发AI Agent应用系列之六：收集资料，向资料库里加资料

loaf 2026-07-17 大约 14 分钟 技术 LLM Agent AI

之六：向资料库中导入素材

前面我们先建了一个资料库的结构，定义了进出资料库的规则。本文开始向库中导入素材。

正文是怎么来的

根据前面的需求，正文来源于以下三个入口：

  1. 粘贴文本

用户直接输入、复制粘贴。因为这已经是字符串了，可以直接调用store.

  1. 上传文件

因为上传的文件有不同的格式，所以需要读出字节，然后抽出标准的文本格式再调用store，所以先得根据扩展名分发抽取。

  1. URL抓取

用户给个链接，使用httpx拉网页，trafilatura提取正文，然后得到文本。这就涉及到刚才提到的工具了，同时还得有网络连接。

上面三个方法，最终都是拿到 content: str，全部调store.save_material(source_type="import")。然后保存、登记 manifest、去重。

抽取工具层 backend/app/kb/extract.py

1.数据结构：ExtractedDoc dataclass

@dataclass
class ExtractedDoc:
    content: str       # 要落盘的正文
    title: str = ""    # 给 manifest 用 (没更好标题时用这个)

这里直接用dataclass而不是Pydantic，是因为它只在内部传递，不跨API边界，没必要搞的很复杂。

2. URL 抓取：fetch_html + extract_text_from_url 拆两层

async def fetch_html(url: str) -> str:
    """抓一个 URL 的 HTML 文本。仅 http(s)。"""
    _validate_url(url)
    async with httpx.AsyncClient(timeout=_TIMEOUT, follow_redirects=True) as client:
        resp = await client.get(url, headers={"User-Agent": _USER_AGENT})
        resp.raise_for_status()
        if len(resp.content) > _MAX_BYTES:    # 防 OOM
            raise ValueError("页面过大")
        return resp.text

async def extract_text_from_url(url: str) -> ExtractedDoc:
    html = await fetch_html(url)
    from trafilatura import extract as traf_extract
    content = traf_extract(html, output_format="markdown", ...)
    if not content:
        raise ValueError("无法从该页面提取正文")
    return ExtractedDoc(content=content, title=...)

[!TIP]
考虑到后面调用AI代理时，可能使用原始HTML更智能（比如需要提链接，找下一页，分析脚本等），所以不必调用trafilatura库来多此一举。所以这里分成两步走。下次代码可复用。

[!TIP]
trafilatura 局部 import：

from trafilatura import extract as traf_extract # ← 局部 import

trafilatura 是重依赖（载入慢、打包大）。放局部 import 的好处：

  1. 不用 trafilatura 的代码路径（比如测试只测 fetch_html）不用载入它，启动更快。
  2. test_extract.py 的 monkeypatch 桩 httpx 时，trafilatura 照常工作（真处理一段测试 HTML）。

3. 文件抽取：四个 _extract_* 私有函数

extract_text_from_bytes(filename, data)   # 入口: 按扩展名分发
  ├─ _extract_plain(data, ext)            # md/txt: utf-8 decode (失败用 errors='replace')
  ├─ _extract_docx(data)                  # python-docx: 逐段拼接
  └─ _extract_pdf(data)                   # pdfplumber: 逐页抽文本

资料API backend/app/api/materials.py

1. 路由表

Method Path 异步? body 状态码
POST /materials/text def JSON {project_id, text, title?, ...} 201 / 200
POST /materials/file async multipart (project_id + file) 201 / 200
POST /materials/url async JSON {project_id, url, ...} 201 / 200
GET /materials def query ?project_id=&source_type=&tag=&keyword= 200

2. 请求/响应模型（Pydantic，定义在路由文件内）

class TextImportRequest(BaseModel):
    project_id: str = Field(..., min_length=1)
    text: str = Field(..., min_length=1)
    title: str = Field(default="", max_length=200)
    snippet: str = Field(default="", max_length=500)
    tags: list[str] = Field(default_factory=list)

class ImportResponse(BaseModel):
    material_id: str
    result: Literal["created", "deduplicated"]

请求模型定义在路由文件而不是 models/ 的原因参照 workflow.py 的习惯：接口专属的请求/响应模型（只这一个路由用）就近放在路由文件，减少跳转。 Material 这种跨接口共用的才放 models/。

3. 项目存在性校验：_require_project

def _require_project(project_id: str) -> None:
    if db.get_project(project_id) is None:
        raise HTTPException(status_code=404, detail=f"项目 {project_id} 不存在")

三个写入接口和 list 接口开头都调它。这是为了防止store自动新建kb目录，然后留下一堆孤儿目录。

4. 文件路由：UploadFile + Form

@router.post("/materials/file", response_model=ImportResponse)
async def import_file(
    response: Response,
    project_id: str = Form(...),          # ← 来自 multipart 表单字段
    file: UploadFile = File(...),         # ← 来自 multipart 文件部分
    title: str = Form(default=""),
    tags: list[str] = Form(default_factory=list),
) -> ImportResponse:
    data = await file.read()
    ...

FastAPI 文件上传的 idiomatic 写法：

  • UploadFile = File(...) 接文件部分。
  • 其他字段用 Form(...) 而不是 Body(...)——因为是 multipart 表单，不是 JSON body。
  • await file.read() 一次性读字节（资料规模小，可接受）。

5. 错误码映射

情况 状态码 理由
项目不存在 404 标准 REST: 资源不存在
空文本 / 空 file / 缺 project_id 422 Pydantic 校验失败, FastAPI 自动返
不支持的文件扩展名 422 参数语义错, 不是服务器错
docx/pdf 抽不出正文 422 同上, 输入有问题
URL scheme 非 http(s) 422 同上
URL 抓取失败 (网络/4xx/5xx) 422 用户给的 URL 有问题, 不是我们服务器挂了
成功新建 201 REST: Created
成功去重 200 REST: OK, 没建新资源

前端 Collect.tsx + client.ts

1. client.ts 扩展：四个函数 + 两个类型

export type SourceType = "search" | "discussion" | "import" | "note";
export interface Material { ... }   // 镜像后端 Material (无 content/vector)

export async function listMaterials(projectId, opts?): Promise<Material[]>
export async function importText(projectId, text, meta?): Promise<ImportResponse>
export async function importFile(projectId, file, meta?): Promise<ImportResponse>   // ★ 不走 apiSend
export async function importUrl(projectId, url, meta?): Promise<ImportResponse>

importFile 是唯一不走 apiSend 的——因为 multipart 不能 JSON.stringify。其他三个函数都复用 apiGet / apiSend，模式一致。

2. Collect.tsx：Tab 切换三入口

{(["text", "file", "url"] as const).map((t) => (
  <button onClick={() => setTab(t)} style={{ ...styles.tab, ...(tab === t ? styles.tabActive : {}) }}>
    {t === "text" ? "粘贴文本" : t === "file" ? "上传文件" : "URL 抓取"}
  </button>
))}

3. “实时刷新”：每次导入成功后 await refresh()

async function submitText() {
  ...
  const r = await importText(projectId, body, {...});
  handleResult("文本", r);
  ...
  await refresh();    // ← 关键: 重新拉列表
}

4. created vs deduplicated 的前端提示

function handleResult(label, r) {
  if (r.result === "deduplicated") {
    setLastResult(`${label}: 资料库已有相同内容 (已存在 id ...)`);
  } else {
    setLastResult(`${label}: 已添加 (id ...)`);
  }
}

后端 ImportResponse.result 字段的语义落点：让前端区分提示。

绿色"已添加" vs 同样绿色但信息更准的"已有相同内容"——让用户知道去重发生了。

5. 路由接入：App.tsx 加 collect 视图

type View =
  | { kind: "list" }
  | { kind: "detail"; projectId: string }
  | { kind: "collect"; projectId: string }   // ← 新增
  | { kind: "chat" };

从 ProjectDetail 点"收集资料 →“进入 Collect；Collect 的 onBack 回 detail（不是回列表）。保持"列表 → 详情 → 子页"的层级感。
