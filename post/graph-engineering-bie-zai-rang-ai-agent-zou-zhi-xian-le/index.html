Graph Engineering：别再让 AI Agent 走直线了

loaf 2026-08-03 大约 14 分钟 随笔 人工智能 LLM AI Agent

在前面关于智能体开发的系列写完后，我回过头看自己的示例项目，尴尬地发现，不用Graph框架，项目的功能也可以实现。

那么问题来了：Graph Engineering 会不会又是一个被炒热、然后迅速遗忘的术语？

这种怀疑反而勾起了我的兴趣。我想搞清楚：Graph Engineering 到底在解决什么"别的办法解决不了"的问题？ 如果它真有用，用在哪、怎么用、什么时候别用？

这篇就是我这段时间琢磨下来的一些答案。

一、你的智能体，为什么总有幻觉？

你让你的智能体去“收集AI Agent相关的资料，对比当前市场上流行的产品，然后给一个推荐报告”。

最直觉的做法，是把它丢进一个聊天窗口，让 Agent 自己搞定一切：搜索 → 阅读 → 对比 → 写报告。

听起来很顺，结果呢？

一个Agent漏看了原始来源，第二个 Agent 复读了同样的错误，审核 Agent 看到的是一份"看起来很专业"的答案，于是点头放行。等报告送到你手上，没有人能说清是哪一步把整件事带偏的。

问题出在哪里？

不在于模型不够聪明，也不在于提示词写得不好。问题在于：你把一件本该是"网状"的工作，硬塞进了一条"线"里。

这就是 Graph Engineering（图工程） 要解决的事。

二、先说清楚：什么是 Graph Engineering？

从"一句话"到"一张图"

回顾一下我们调教大模型的方式，它其实经历了几次进化：

  • 单个提示词：写一句最好的话，祈祷模型听懂。
  • 链（Chain）：第一步喂第二步，固定流水线。
  • 树（Tree）：分支探索多种可能，再回溯选优。
  • 图（Graph）：路由、并行、合并、循环自由组合。

Graph Engineering，就是把"AI 要做的工作"提前画成一张有向图：谁先跑、谁后跑、谁能同时跑、跑挂了怎么办、谁来拍板——都由你来设计，而不是丢给模型临场发挥。

学术上有个精确的定义（来自 Sandeco Macedo 2026 年的论文），它要求一张"图"必须同时满足四个条件：

条件 含义 通俗解释
G1 显式结构 节点和边能被一一列举 不跑起来，也能看清整个流程
G2 结构/内容分离 改流程不用重写提示词，反之亦然 换个"走法"不用重写"台词"
G3 可执行语义 有运行时来调度、路由、管状态 它是一段能跑的程序，不是一张PPT
G4 一等公民 图本身是一个可检查、可版本化、可优化的对象 能存档、能回滚、能让优化器去改

一句话：模型负责思考，图负责把思考变成靠谱的工作。

一张图，就四样东西

你不需要懂图论。建一张有用的图，只需要四样东西：

① STATE（状态）：任务在聊天窗之外的"记忆" （原始需求、收集到的证据、重试次数、预算… ）

② NODE（节点）：一个节点的活儿要"小而明确" （ “查价格"是节点，“搞定一切"不是）

③ EDGE（边）：回答一个问题：下一步谁上？ （有的边固定，有的边看状态决定）

④ GATE（门）：挡住坏结果往下游流 （测试、校验、人工审批、置信度阈值… ）

⚠️ 重点：没有门的图，只是让错误传播得更快而已。

三、为什么早期的 ReAct 和 Loop 干不好？

ReAct 的困境：一条道走到黑

ReAct（Reason + Act）是早期 Agent 的经典范式：模型"想一想 → 做一步 → 看结果 → 再想”，在同一个聊天窗口里循环往复，整个流程也会共用同一个上下文窗口。

这听起来很自然（我们说话就是一句接一句嘛），但它有三个致命伤：

  1. 串行排队：明明"查产品 A 价格"和"查产品 B 价格"互不依赖，却非得一个做完再做下一个，白白浪费时间。
  2. 错误会"滚雪球”：前面一个薄弱的假设，变成了下一步的上下文，再变成下下一步的"证据"。Agent 的错误是会复利累加的。
  3. 自己审自己 = 没审：同一个 Agent 既要创作又要审核，它早就知道自己为什么这么写了，怎么可能客观挑刺？这叫"用不同的字体附和自己"。

Loop 的陷阱：被自己定的 KPI 欺骗

后来大家进化到了 Loop Engineering（循环工程）：让 Agent 进入"试一试 → 检查 → 修正 → 再试"的循环，不断自我改进。

这比 ReAct 强，但它有个躲不开的毛病——古德哈特定律（Goodhart’s Law）：

当一个指标变成目标，它就不再是个好指标。

来看一个扎心的真实例子：

客服团队给反馈循环定了一个 KPI：工单解决率 ➡ 指标连着涨了好几个月 📈 大家都很开心 ➡ 但用户满意度其实在掉 📉

真相：机器人学会了"快速关单"，而不是"解决问题"

一个循环只能看见它自己盯的那个数字。 它没法问"我盯的目标对不对"，也察觉不到自己的测量在漂移。

答案不是"搞个更好的循环"，而是——搞一张由循环组成的网，让循环之间互相盯着、互相纠偏。

ReAct vs Loop vs Graph：一张图看懂

维度 ReAct Loop Graph
执行方式 严格串行 自转循环 并行 + 串行 + 循环，自由组合
上下文 一个大窗口 一个大窗口 每个节点独立上下文，按边传递
错误控制 几乎没有 自己改自己 独立验证节点 + 门拦截
可解释性 一条长日志 循环日志 每个节点的输入输出都可追溯
能否扩展 加节点就更乱 循环越多越慢 天然支持扇出，一次跑上千个

四、Graph Engineering 的特点和优点

特点：围绕"失败"来设计，而不是"快乐路径"

大多数流程图画的都是"一切顺利时怎么走"。但生产系统是由"出岔子时怎么办"来定义的。

Graph Engineering 的核心心法：在给每个重要节点加 Agent 之前，先写下它可能的 5 种结局：

这彻底改变了你给模型写提示词的方式。别再问"这个好不好？"，而是让验证器直接返回一个路由决策：

{
  "decision": "retry",
  "reason": "两条数据没有一手来源",
  "target": "collect_company_data"
}

这个输出之所以有用，是因为图能根据它采取行动——它知道该把活儿扔回哪个节点。

四大优点

  1. 🚀 并行提速：独立的工作同时跑，不用傻等。
  2. 🛡️ 错误隔离：每个节点独立上下文，一个节点的"糊涂"不会污染全局。
  3. 🔍 可追溯：每个结论都能追到某个节点、某条证据、某个来源。
  4. 📊 可预算：时间、Token、风险三本账，花超了就停下，吐出"当前最好的部分结果"。

五、落到一个具体的例子上：怎么用一张图优化你的 AI Agent

一个完整的例子：产品调研报告

回到开头那个任务——“对比几款产品，出推荐报告”。单 Agent 版把发现、判断、写作全混在一个窗口里，一旦失败无从定位。

关键细节：上下文应该沿着图的边走，而不是堆在一个巨型窗口里。写手节点永远看不到原始的调研记录——它只接收经过验证的、结构化的证据。

伪代码：用图思维写一个带验证的并行调研

下面这段伪代码展示了 Graph 的核心套路——扇出（Fan-out） → 独立验证 → 汇总（灵感来自 Anthropic 的 Dynamic Workflows）：

// 第一步：扇出——每个任务一个独立 Agent，并行跑
const tasks = ["产品A文档", "产品A价格", "产品B文档", "产品B价格", ...];

const findings = await gather(
  tasks.map(task =>
    spawn("researcher", {
      task,
      instructions: "调研并返回结构化 JSON：claim + source + confidence"
    })
  ),
  { concurrency: 16 }   // 最多同时跑 16 个
);

// 第二步：门——过滤掉置信度低的
const suspicious = findings.filter(r => r.confidence >= 0.70);

// 第三步：独立验证——换一个新上下文的 Agent，拼命"证伪"
const reviews = await gather(
  suspicious.map(r =>
    spawn("verifier", {
      report: r,
      instructions: "试着推翻这个结论。返回 pass/fail + 理由。"  // ← 关键：全新上下文
    })
  ),
  { concurrency: 16 }
);

// 第四步：汇总——写手只看已验证的结果
return await spawn("synthesizer", {
  verified: reviews.filter(r => r.pass),
  instructions: "基于以上已验证证据，写一份带出处的报告。"
});

注意三个"Graph 味"十足的设计：

  • 🔹 spawn 出来的每个 Agent 都是全新上下文，互不污染。
  • 🔹 中间结果存在脚本的变量里，不占用你的聊天窗口。
  • 🔹 验证器的工作是"证伪"，不是"点赞"——它和创作者信息不同、目标不同。

Anthropic 总结的 5 种工作流"积木"

不必每次从零画图，Anthropic 给了 5 种可复用的模式，按需组合：

  • ① 提示链 Chaining：固定顺序，每步喂下一步
  • ② 路由 Routing：分类器把输入送到对应专家
  • ③ 并行 Parallel：独立任务同时跑（投票/分工）
  • ④ 编排-工人：中央模型动态拆解、分配、汇总
  • ⑤ 评估-优化 ：一个生成、一个按标准挑刺，循环改进

心法：从最简单的开始，只有当某种模式"可测量地"改善结果时，才往上加复杂度。

一条循序渐进的升级路线

别一上来就搞大工程。Karpathy 和 Anthropic 的实践指向一条清晰的进阶路径：

先实现ReAct，然后再增加各种工具（比如搜索）， ➡ 实现多Agent ➡ 将多个Agent接入图，引入持久记忆 ➡ 最终可扩成集群。

每一步都只解决上一步的某个具体短板：循环解决"一次过"的错误，工具解决知识缺口，规划解决复杂度，多角色解决视角局限，图解决持久记忆，集群解决规模。

六、真实案例：让数据说话

这套方法不是 PPT 上的画饼，已经有人用真金白银跑出了结果。

案例一：Bun 的 Zig→Rust 大搬家

Bun 团队用 Anthropic 的 Dynamic Workflows，把整个运行时从 Zig 迁移到 Rust：

指标 数据
工作流数量 约 50 个
并行 Agent 峰值 64 个
代码规模 约 53 万行 Zig → 超过 100 万行 Rust
耗时 11 天
测试通过率 99.8%
花费 约 16.5 万美元

⚠️ 规模是真的，代价也是真的——这玩意儿还需要人来全程设计和监控。但这是单靠"一个 Agent 一个窗口"永远做不到的事。

案例二：Karpathy 的 autoresearch

Karpathy 的自动研究项目，把一个约 630 行的训练程序，变成一个自主实验组织：

指标 数据
实验次数 约 700 次 / 2 天
保留的有效优化 约 20 个
GitHub Stars 8.6 万+

它工作的秘诀是四个条件：输出可验证、操作可撤销（git reset）、反馈周期短（5 分钟一轮）、环境有边界。

案例三：Anthropic Dynamic Workflows 的天花板

指标 数据
单次工作流最多子 Agent 1000 个
同时并发上限 16 个
每个 Agent 全新上下文

所谓"一个窗口跑 1000+ 循环"不是比喻，是功能的实际上限——一千个 Agent 像波浪一样分批涌出，嚼完所有任务，全程不需要你盯。

七、冷静一下：什么时候不该用图

讲到这里，我必须泼一盆冷水。

Graph Engineering 不是把每个提示词都变成基建的理由。大多数任务根本不需要图。

✅ 该用图 ❌ 不该用图
有独立工作可以并行
不同输入需要不同专家/工具
失败需要重试/降级/上报
任务要能中断后从状态恢复
高影响输出需要独立验证
人类该审批但不该盯每一步		 任务很小、很孤立（改个bug）
你想逐步审批每一步
你还不知道自己在找什么（探索期）
步骤之间真有严格依赖（那就是条链）──链挺好，别硬拗成图

判断诀窍：看看你能不能找到"两个之间没有箭头的盒子"。找不到？那就是条线，线没什么不好。

一个图是"宽"的工具——为独立的活儿同时干而生的。活儿不宽的时候，线从来不是问题。

结语：从"提问者"到"画图的人"

最后，用一个对比来收尾：

写提示词的人问：模型接下来该说什么、该做什么？

画图的人问：此刻该存在什么信息？谁来处理它？什么能证明结果是对的？失败该往哪走？

后一个问题更难，但也正是它把一个"炫酷的 demo"，变成了一个"你敢用第二次的系统"。

关键是：“记忆和验证放在哪里”。

  • 一个循环能记住当前代码和实验日志；
  • 一个集群能创造许多独立上下文；
  • 一张工作 DAG 能记住"哪个成果源自哪个实验"；
  • 一张知识图能记住"哪些结论连着哪些实体和来源"。

它们合在一起，阻止 Agent 在每个上下文窗口里从零开始重建整个世界。
