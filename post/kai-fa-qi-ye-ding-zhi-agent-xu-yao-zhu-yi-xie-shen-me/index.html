开发企业定制Agent需要注意些什么

loaf 2026-09-16 大约 8 分钟 技术 Agent

当你为企业定制Agent时，你首先需要问的是：为什么要自己开发？

当前市面上有许多现成的智能体，直接使用不是更好吗？

接着需要问的是，怎么才能写好一个Agent？

本文将从头梳理一下我们决策的思路。

Harness与模型的耦合关系

网上到处是用Claude Code接上DeepSeek，用Codex调用GLM的文章。大家也津津乐道于OpenCode能随意切换不同的模型。

事实上除国外闭源的几个模型公司外，大多数的Agent产品，哪怕有自家模型，也都提供了切换第三方模型的功能。

大家都知道，智能体=控制+模型。

这里的控制，就是Harness。简单来说，智能体中，除大模型以外的所有代码——哪些搜索结果进入上下文、工具怎么暴露给模型、JSON 解析失败怎么重试、交互什么时候停止等等，都是Harness的范畴。

我们习惯于频繁切换模型，或者因为额度限制，或者因为成本。但我们往往忽略了一个真相：一个智能体的能力并不能简单地理解成Harness和模型权重之和。

关于这一点，我们从一篇论文1 中得到了佐证。

这篇由KRAFTON 联合斯坦福、KAIST 完成的论文叫WHALE（Weight–Harness Alternating LEarning）。它提出权重和Harness交替学习的一种Agent开发策略。

具体的实现原理非常简单（作者自己就管它叫 “a simple recipe”）：

  1. 冻结Harness，更新权重。用 RSFT（在线拒绝采样微调）：拿当前 Harness 跑 rollout，只挑模型自己跑出来、且通过验证器的样本当训练数据；
  2. 冻结模型，搜索 Harness。一个叫 Meta-Harness 的“提议者 Agent”（实验里是 Claude Opus 4.7）读所有候选 Harness 的源码、分数和轨迹，提议新 Harness，在固定的训练样例上打分，选择最好的代码；
  3. 回到第一步。

总结一下就是：

Harness和大模型的关系比我们想象的要复杂。并不是说最强的Harness配上最智能的模型，就能组合成一个最强的智能体。智能体的调优，是有工程学上的理论依据的。

简单来说，就是先不动代码，只专注在权重上做后训练，能力提高到一定值后，再冻结权重，专注Harness代码的调优……，交替优化

论文讨论提智能体优化的路径，但在我们实际工作中，对权重文件进行SFT的可能性很小，大多数企业并没有这个能力。我们能做的也只是对Harness代码进行优化。

但这就会面临一个问题，一旦模型升级，或者模型替换，你为企业精心打磨的Agent就会崩掉。以前，我们叫“玄学”或者“工程债”。现在这篇论文给它起了一个学名：条件过度拟合（Conditional over-optimization）

企业Agent不应该是通用Agent

按照WHALE论文的核心结论：Harness 的有效性以模型为条件。而通用Agent要支持多个模型，Harness只能取“公共交集”，等于放弃了对任何单一模型的深度优化。这是结构性的妥协，不是工程失误。

所以，当我们写一个企业Agent时，应该尽可能避免通用化。

  • 应该尽可能用固定的模型，最好是本地模型，冻结模型权重。只有确定的模型，代码的优化才有意义。

  • 有条件的情况下，才对本地模型进行SFT。

  • 尽量只做调度路由，复杂问题交给第三方智能体。第三方智能体（Claude Code 这类）是“模型 + Harness 已 co-evolve 好的成品对子”，造不如买。

当然，如果只做路由的话，在实际中也会遇到一些问题，目前能想到的就是：

  1. 调试黑洞。出了问题，很难归因。你不知道是自己的路由烂还是第三方的智能体不行。
  2. 数据安全。内部数据出域时需要清洗，返回后还要重新拼装。
  3. 成本问题。高频流程按Token计费本来就贵，加上这种调用相当于将第三方智能体当作无状态的工具，就无法利用到智能体内部的上下文缓存等优化功能。

企业Agent应该成为一个傻瓜式的工具

你不应该希望你的企业Agent是一个数字员工，而应该让它成为你的数字助理。

数字员工被定义为能做多种事，代价是复杂且行为不可预期；数字助理绑定一条固定工作流，只做一件事。

企业Agent的价值在于稳定而不在于全能。

企业Agent作为一个数字助理，它的作用是代替用户操作各种平台，并把复杂工作路由给第三方智能体完成。它有人格（专长、特点）、能保存使用者的长期用户画像，并随使用次数增加越来越懂用户。就好像一个真实的人类助理，帮领导做的事情越多，越了解领导的习惯和偏好。

和真实助理不一样的地方在于，人类助理是全能的，而这个数字助理只能做好一件特定的事。当然，多个不同数字助理组合在一起也是可以代替人类助理的。

数字助理 = 以 LLM 为决策脑、以 skill 为可换策略、以第三方智能体为外派执行者、以记忆文件为唯一持久状态的固定工作流引擎。

对于一个数字助理，我们用三层对象模型来描述：

层 对象 特性
定义层（引擎） 工作流模板 + 可用 skill 清单 + 绑定的记忆视图 + 允许的外派目标 常驻、可版本化
运行层（实例） 一次任务触发的助理实例 易逝，可丢可留
状态层（记忆） 用户人格 + 用户信息 + 任务记忆 持久、跨实例、跨岗位共享

因为数字助理做事的原子性，自然会涉及到数字助理间的数据共享，比如多种任务可以由一个用户触发，这时它们共享一个人格文件，这样减少同步代价也不会遇到共享锁的问题。

这就引入了另一个需求，岗位分类，需要增加一个管理岗位。这个管理岗位本质上也是一个数字助理，只是它的任务是协调其它的助理，相当于部门领导。

工作流骨架（普通代码，写死）与大脑决策点（LLM 调用）分离。以生成型岗位为例，六步流水线：

读人格 → 读资料 → 拼提示词 → 外派 → 审核验收 → 记忆写回

大脑只在四个决策点被调用，其余环节为确定性代码：

  1. 读什么——不全量注入人格/信息，按任务特征选相关片段（检索策略，skill 为载体）
  2. 怎么拼——模板、风格、结构的策略选择
  3. 怎么初筛——帮审核人省力（如产物溯源行）
  4. 记什么——记忆提案的产生

管理岗也是岗位：它的“一件事”是调度本身——冲突仲裁、提案落盘、任务分解/分派/汇总/交付人审。

企业Agent如何实现知识库

AI时代，当我们说为企业设计知识库时，想到的技术就是各种RAG技术细节，什么chunk切片，什么嵌入模型，什么向量数据库，不一而足。

当我们写企业Agent时，也第一个会想到智能客服，这不正是智能体所能做的吗？

但有趣的是，大多数Agent里，你很少看到关于RAG的代码部分。这是因为 Agent 把 “检索决策” 从工程系统交还给了模型，而 “用向量猜” 在有精确访问路径的场景里是劣化方案；同时 Agent 的真正瓶颈在控制与决策，不在信息获取。

RAG 隐含三个假设，在 Agent 场景里全部不成立：

RAG 的假设 Agent 的现实
检索时机预先已知（问题→query 直接映射） 检索需求是执行中涌现的（“我改了这个函数，得看谁调用了它”）
检索是一次性的（生成前检索完） 检索是迭代、反馈驱动的（读到一半发现需要别的信息）
相关性可用向量相似度离线近似 相关性由模型在上下文中动态判断

另外，如今的大模型拥有越来越大的上下文，这使得RAG的应用场景大大缩小。

所以，企业Agent里不应该实现RAG，这不是放弃了检索，而是把检索从“架构范式”降格为“可随时调用的工具”。这个转变由三件事共同驱动：模型获得了自行决定检索的能力（内化）、精确访问路径在 Agent 场景中普遍存在（劣化向量检索）、以及 Agent 的真正瓶颈在决策控制而非信息获取（注意力转移）。

但是企业内部还是需要企业知识库啊。

我们的方案是企业知识库作为外部能力（Agent 应用或检索 API）通过一个适配层 skill 接入。

知识库可以是另一个 Agent 应用，也可以只是检索 API。

两条边界：

  1. 知识库只以工具形态进入既有岗位工作流（“读资料”步），用户想直接查资料时，入口应该是知识库应用本身；
  2. 检索结果仅作任务资料，不入记忆。

结语：回到开头的问题

为什么要自己开发？ 因为智能体的能力并不是Harness与模型的简单相加，而是两者深度耦合的结果。通用Agent为了兼容多个模型，只能取Harness的“公共交集”，放弃了对任何单一模型的深度优化；而企业场景恰恰需要这种深度优化带来的确定性。

怎么才能写好一个企业Agent？ 答案是做减法：

  • 锁定一个模型，所有Harness的打磨都建立在这个确定的前提上；
  • 不做全能的数字员工，只做单一职责的数字助理，用稳定换价值；
  • 不自建RAG，把知识库当作外部能力，经skill接入固定的工作流；
  • 复杂问题外派给第三方智能体，自己只保留调度、审核与记忆。

模型会不断升级，精心打磨的Harness也可能随之失效，这件事没有一劳永逸的解法。但企业真正需要掌握的是业务流程、数据边界、用户记忆等不变部分。把这些不变的部分沉淀成自己的数字助理，是企业定制Agent的全部要义。
