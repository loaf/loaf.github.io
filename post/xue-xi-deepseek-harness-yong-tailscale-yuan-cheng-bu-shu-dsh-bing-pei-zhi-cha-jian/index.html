学习Deepseek Harness：用Tailscale远程部署DSH并配置插件

loaf 2026-08-18 大约 11 分钟 随笔 人工智能 DeepSeek Agent

先在服务器上部署一个DSH

在本地，当然是从源码部署，但是在远程服务器上，可以简单一点，直接运行npx命令来运行。

但是要注意，当前的dsh web只支持本机访问，也就是说，只能通过127.0.0.1这个IP地址访问。

我是使用Tailscale来远程访问的。

首先，我的服务器上已经安装了node，就不用管它了。为了后台运行服务，又安装了一个pm2。

pm2 start npx --name "dsh-web" -- @deepseek-ai/dsh web

[!TIP]
常用管理命令：

查看所有进程状态：pm2 list 或 pm2 status
停止应用：pm2 stop dsh-web
重启应用：pm2 restart dsh-web
删除应用：pm2 delete dsh-web
查看日志：pm2 logs dsh-web

设置开机自启（可选）：

pm2 startup
pm2 save

这个命令会生成一段脚本，运行后能让 pm2 在系统重启时自动恢复之前保存的进程列表。

这时从外网是不能访问的，通过Tailscale serve来穿透。

tailscale serve -bg 3080

[!TIP]
要关闭它，使用

tailscale serve --https=443

运行后，它会提供一个证书和域名，你直接访问这个域名即可打开dsh。

但是，你在运行时会发现报错，并不能正常使用。这是因为 dsh 出于安全考虑设计的“回环限制（loopback restriction）”机制导致的。

简单来说，为了安全，dsh 的 Web UI 默认只信任来自本机（127.0.0.1 或 localhost）的访问。当你通过 Tailscale 的域名（如 xxx.ts.net）访问时，请求来源不再是本机，因此触发了安全限制，导致 API 请求被拦截，配置页面无法正常加载。

pm2 stop dsh-web
pm2 start npx --name "dsh-web" -- @deepseek-ai/dsh web --trusted-host your-machine.ts.net

这时，就能访问web页面，进行对话，但是在设置页面的大多数项目中都会出现：transport failure for /api/settings.describe: HTTP 403，这个是源代码里故意写死的。

settings.describe 在 PRIVILEGED_METHODS 列表里（line 511），这类方法被刻意钉死在 loopback—— 注释写得很清楚：“privileged methods additionally pass it with an empty trust list, which pins them to loopback”。也就是说无论 –trusted-host 配什么，远程访问特权 API 一律 403，这是防 DNS-rebinding / 跨站攻击的安全设计。

解决方案有两种。一种是SSH端口转发，在客户端机器上建立隧道。另一种方法是修改源码。因为我这里主要是测试用，而且使用了Tailscale serve，所以我决定修改源码。

把 dsh-client-connection/lib/index.js 第 538 行的 isTrustedApiRequest(request, []) 改为 isTrustedApiRequest(request, trustedHosts) 可以让远程访问特权 API。但会引入 DNS-rebinding 风险，且 npm 更新会被覆盖。

好在这台机器上原来安装过hermes，我直接让它修改，它自动修改了，我现在可以通过tailscale serve直接访问了。

为DSH增加插件

在服务运行时，会在用户目录创建一个名为.dsh的隐藏目录。

当前我用root登录的，所以DSH_HOME=/root/.dsh，profile 位于 /root/.dsh/profiles/。

这里DSH_HOME可以理解为一个实例。如果你要在一台服务器上运行多个Agent实例，就需要建多个DSH_HOME。

我们看一下.dsh目录下的内容：

.dsh
├── profiles
│   └── web
│       ├── cordis.patch.yml
│       ├── cordis.yml
│       ├── package.json
│       └── pnpm-workspace.yaml
├── sessions
│   └── ...
├── settings.yaml
└── storages
    ├── session_projcache.json
    └── workspace.json

sessions下是会话内容。

当前profile只有一个web，就是我们正在用的这个GUI，如果你后面要增加其它的交互方式，比如用微信、飞书等，会有新的目录。

我们看web下的package.json文件

{
  "name": "dsh-profile-web",
  "private": true,
  "dependencies": {},
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app"
      ]
    }
  }
}

我先在github上找一个插件，zhu1090093659/dsh-web-ui挺好。我先只安装主题皮肤。

npx @deepseek-ai/dsh plugin –profile web add @linxin666/dsh-skins@latest

完成后再看web下的package.json文件:

{
  "name": "dsh-profile-web",
  "private": true,
  "dependencies": {
    "@linxin666/dsh-skins": "^0.1.20"
  },
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app",
        "@linxin666/dsh-skins"
      ]
    }
  }
}

pm2 restart dsh-web，重启后就能看到皮肤中心了。
npx @deepseek-ai/dsh web –restart

处理“历史加载失败：The user aborted a request (internal) ”错误

但是我在打开某些会话时，会出现“历史加载失败：The user aborted a request (internal) ”错误。

遇事不决问AI，DeepSeek说，这个报错通常意味着会话的历史日志文件已损坏，DSH 在加载时无法按顺序读取。是因为我上面反复强制重启、安装皮肤，引起了DSH 的会话日志文件出现了数据冲突或损坏。

DSH 的每个会话都对应一个日志文件（通常是 ~/.dsh/sessions/…/session.jsonl.zstd）。当服务异常关闭（如进程被强制结束）或有多个进程同时尝试写入同一个日志文件时，就可能造成数据损坏。

损坏的典型特征是日志中的事件序号（seq）出现了回退（seq gap），即新写入的事件序号小于已存在的序号。当加载器发现序号不连续时，就会拒绝加载整个历史，并抛出类似“corrupt session log: seq gap…”的错误。

最简单粗暴的解决方案是删除这个会话。

先删除会话内容：

rm -rf ~/.dsh/sessions/--root-dshwork--/session-19fcc9d1-3524-4d11-9f6f-f12e394c8166/

找到这个session id的方法也比较简单，你可以在出错的会话中，点击右上角的session log下载，下载的文件名就是对应的session id号。

然后还有两个地方需要处理：

数据 位置 作用
工作区注册表 ~/.dsh/storages/workspace.json 这就是"会话列表"的持久化账本：workspaceIds 顺序、每个工作区的 sessionIds 有序列表、archivedSessionIds
会话投影缓存 ~/.dsh/storages/session_projcache.json 每个会话的标题/统计等缓存

这两个地方需要在服务器停止时处理。

因为自己处理比较麻烦，其实最简单的方法是开一个新会话，然后把问题抛给AI，它会自己处理这些问题。它不能处理的，会给你一个脚本，让你在停止服务后自己运行。
