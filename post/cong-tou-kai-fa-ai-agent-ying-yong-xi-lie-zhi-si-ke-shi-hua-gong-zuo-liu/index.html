之四：让工作流可视化

本章的目标是：让工作流可视化，同时能让用户直观地看到项目列表，并可以对列表进行增加、删除操作。在文章的最后，能你看到完成后的视频。

项目vs工作流

项目是稳定、长期的实体，在此可以简单地理解成一篇文章的生命周期（比如，我要写一篇关于AI Agnet的文章，文章标题是“AI Agnet开发”），工作流是一次性的执行（“我点了生成文章的按钮，跑到某处停了”）。

一个项目可以对应多次工作流——重启、回退、重跑都会产生新的工作流。

所以 Project 表里有个 workflow_run_id 字段，指向当前这一次 run。它是个外键（FK），但不是强约束。

  • 新项目从没启动过 → workflow_run_id = NULL
  • 启动工作流 → 指向新建的 run
  • 旧的 run 历史在 workflow_runs 表里都还在（按 project_id 关联），FK 只是指"当前这次"

数据层 backend/app/db.py

  1. projects 表结构
CREATE TABLE IF NOT EXISTS projects (
    id              TEXT PRIMARY KEY,
    title           TEXT NOT NULL,
    status          TEXT NOT NULL,        -- collecting/generating/finalizing/publishing/archived
    workspace_path  TEXT NOT NULL,        -- 项目工作目录绝对路径 (含 kb/)
    workflow_run_id TEXT,                 -- 当前 workflow run 的 FK (可空)
    created_at      TEXT NOT NULL,
    updated_at      TEXT NOT NULL
);

其中，字段 status 可取下面5个值，这5个值分别对应工作流的阶段情况如下：

projects.status workflow stage 关系
collecting collect 对应阶段1，资料收集中
generating generate 对应阶段2，生成初稿
finalizing finalize 对应阶段3，人工定稿
publishing publish 对应阶段4，发布
archived — 额外的：归档（不再活跃）
  1. CRUD函数
def create_project(title, workspace_path, *, status="collecting", conn=None) -> str: ...
def get_project(project_id, conn=None) -> dict | None: ...
def list_projects(conn=None) -> list[dict]: ...          # 按 created_at 倒序
def update_project(project_id, *, title=None, status=None, workflow_run_id=None, conn=None) -> bool: ...
def delete_project(project_id, conn=None) -> bool: ...   # 只删行, 不删磁盘目录

这里，delete_project 不删磁盘目录。删目录是更危险的操作（不可逆）， 让它在 API 层做（那里能做路径安全检查、能返回合适的 HTTP 错误），DB 层只管删行。 这种"DB 层纯、副作用集中在 API 层"的分工，让 DB 函数好测、好复用。

  1. 数据操作接口 get_latest_workflow_run
def get_latest_workflow_run(project_id, conn=None) -> dict | None:
    """取某项目最新的一条 workflow_run (按 updated_at 倒序)。"""
    row = c.execute(
        "SELECT * FROM workflow_runs WHERE project_id = ? "
        "ORDER BY updated_at DESC LIMIT 1",
        (project_id,),
    ).fetchone()

Pydantic 模型 backend/app/models/project.py

新建 app/models/ 包，在这个目录里，我们将放置所有流程中需要流转的实体。简单说，要放在数据库里的东西都可以放在其中。这里选择Pydantic模型实现。

class ProjectCreate(BaseModel):
    title: str = Field(..., min_length=1, max_length=200)

class ProjectUpdate(BaseModel):
    title: str | None = Field(default=None, min_length=1, max_length=200)
    status: ProjectStatus | None = None

class WorkflowSummary(BaseModel):
    run_id: str | None = None
    stage: str
    node: str | None = None
    status: str
    next_nodes: list[str] = []

class Project(BaseModel):
    id: str
    title: str
    status: ProjectStatus
    workspace_path: str
    workflow_run_id: str | None = None
    created_at: str
    updated_at: str
    workflow: WorkflowSummary | None = None   # 仅详情接口附带

请求模型 vs 响应模型分开：

  • ProjectCreate / ProjectUpdate 是用户能传的字段（只有 title、status，没有 id/workspace_path 这些系统管的）。
  • Project / ProjectListItem 是完整视图（DB 行的全部字段 + 可能附带的 workflow 摘要）。

PS.
这也是对象化编码的代价之一了，其实真正需要建模的只是 Project 。ProjectCreate之类，只是为了控制边界。

API路由 backend/app/api/projects.py

再在api目录下增加一个路由文件。

路由挂在 /api/v1 下，和 workflow 路由同级：

GET    /api/v1/projects            列表
POST   /api/v1/projects            创建(同时初始化 kb/ 目录 + 空 manifest)
GET    /api/v1/projects/{id}       详情(含工作流状态摘要)
PUT    /api/v1/projects/{id}       更新 title/status
DELETE /api/v1/projects/{id}       删除(连同工作目录)

资料库目录结构:

{data_dir}/workspace/{project_id}/kb/
  ├── manifest.json
  ├── pages/
  ├── notes/
  └── images/
  • pages/ 里放抓取的网页
  • notes/ 里放手写的文本和讨论的总结文本
  • images/ 是放图片

ps.
创建项目时要求两步写，第一步在数据库中创建UUID，然后拿到这个UUID，再在第二步时，更新内容。当然，也可以在API层创建UUID，但是这违背了“DB层负责成主键”的原则 。

ps.
为了让项目和工作流中的FK一致，在api./workflow.py的 start_workflow 末尾增加了一行：

db.update_project(project_id, workflow_run_id=run_id)

    // FastAPI 错误体 {detail: "..."} → Error
    let detail = `HTTP ${res.status}`;
