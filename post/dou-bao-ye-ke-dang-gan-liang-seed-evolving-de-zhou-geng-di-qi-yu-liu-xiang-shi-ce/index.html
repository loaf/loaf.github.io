豆包也可当干粮：Seed-Evolving的周更底气与六项实测

loaf 2026-08-07 大约 12 分钟 随笔 LLM

豆包的用户规模稳居国内第一，但技术社区的讨论热度却远不及 DeepSeek、GLM 或Kimi K3，后者往往成为“国产模型”的代名词，而豆包留给业界的印象大多停留在 Seedance 这一标签上。

8 月初，字节跳动发布了 Doubao-Seed-Evolving，官方宣称其“高频迭代，持续进化 Coding 与 Agent 能力”。综合现有信息，这款模型很可能是 Seed 2.0（Pro 档）面向开发者和 Agent 场景的专门优化版本。

面对这一“进化版”，我们既关心其底层设计理念，也好奇其真实落地效果。因此，本文前半部分将聚焦工程视角，拆解“Evolving”的技术内涵，并对模型结构和发展路径做合理推演；后半部分则转向实践，通过 6 个典型评测案例，客观评估当前版本在实际场景中的表现。

Evolving体现了技术实力

这里的 “Evolving” 指的是产品发布机制，而非字面意义上的“自我演化”，形容的是这条产品线持续滚动发布新版本的运营策略，而非单个模型实例的在线学习。

根据官方说明，它的真正意思是，模型ID不变，但模型本身按周迭代，始终保持在最新状态。

高频迭代的勇气就是实力的体现

模型 ID 不变而模型始终最新,写过代码的人很容易理解：做一个别名路由即可。别名不变，调用时由路由网关解析到某个具体版本的推理集群。

但是在生产环境里会有一些需要考虑的问题：

  • 新版本出现Bug怎么办？
  • 版本的向后兼容怎么解决？

从工程学角度推测，应该是自主控制的灰度发布流程：

关键在于线上指标监控，但监控的重点不在新版本的性能，而在它有没有破坏旧版本原有的能力与调用方式。

这种兼容性的问题，有一个专门的术语 行为漂移（Behavior Drift）。

就是说，模型能力没变差，但"做事方式"变了——导致你原来的 prompt、工作流、参数设置在新版本上表现异常。

这非常考验厂商的技术能力：由于大模型训练的特性，模型性能变强的同时，几乎必然伴随行为漂移。

大模型训练以目标为导向：在深度学习中，奖励函数只约束终点，无法控制路径。所以每次训练都可能走一种新的路径——也许更短，也许更长，但必然和你熟悉的那条不一样。

所以，字节敢承诺发布Evolving版本，并且以周为单位迭代，确实很有勇气。这也算是对自己技术能力的自信吧，这体现的是对自身技术能力的自信——不光是代码能力，更是工程实施能力。

持续训练的数据飞轮是核心，产品架构是基础

人家几个月才出一个版本，字节每周一个小版本，这可不是仅仅靠加班能赶出来的。

首先是数据从哪里来。答案是：生产环境本身就是数据工厂。

用户调用本身会带来真实任务数据和工具调用轨迹数据，对这些数据的筛选后，自然也可以成为训练的样本。

其次，模型架构支持这种高频的更新。

这又要从Doubao Seed系列模型的特点说起了。

大模型多模态化有两条路线——

  • 联合训练（Joint）：从零开始图文混合预训练（如 Gemini路线）
  • 后期整合（Post-hoc）：先训好纯文本 LLM，再"外挂"视觉能力（如Qwen-VL 路线）

从字节的官方文档 [1] [2] 中，我们能了解Seed系列的多模态训练机制选的是后者。原因是"便于消融实验和快速迭代开发"——这非常符合 Evolving 每周更新的产品节奏。

从模型的结构上来说，应该是基于文本的LLM通过一个连接器附加上Seed-ViT视觉编码器。

合理的推测是：语言模型是独立的、先在数万亿纯文本 token 上训好的，视觉能力是之后"嫁接"上去的。图片不是转成文字 token 统一训练，而是：

图片 → Seed-ViT 编码 → 视觉特征 → MLP 适配器 → 映射为 LLM 可读的 embedding → 与文本 token 混合进入 LLM

结合 Seed1.5-VL 论文[1] 的训练配方，每周迭代大概率是：

组件 更新方式 成本
LLM 主干 不重训（预训练太重） 0
适配层 / 后训练 每周增量 SFT + RL（用新收集的数据） 中
视觉编码器 低频更新（视觉能力变化慢） 低
推理策略 每周调优（prompt 模板、CoT 长度、温度） 低

⚠️ 注意：“每周迭代” ≠ “每周重训预训练模型”。预训练需要数周和巨额算力。周更大概率是后训练层迭代（SFT/RL 数据更新 + 策略优化），因为 Seed 系列正是"后期整合"架构——文本 LLM 稳定，外层能力可以高频更新。这也解释了为什么 Evolving 的能力提升集中在 Coding 和 Agent（这两个方向的数据飞轮最快、反馈信号最清晰：代码能跑不能跑、任务完成没完成）。

模型的长程任务能力

字节对于长程任务的定义是：

“real-world tasks span long horizons and multiple stages, but existing LLM agents struggle to autonomously construct effective workflows and accumulate experience over extended timescales.”

也就是说，字节认为，长程任务的目标是独立交付一个真实的工程。特点是，多阶段、需自主构建工作流、跨多个工具/文件/时间步、需在长跨度上维持状态与累积经验。

事实上，从各项基准测试来看，豆包的Seed系列模型在这类任务上的得分仍是落后于国外主流模型的。

字节将长程任务组织成4个维度，分别是：科学发现、Vibe Coding、真实的软件工程（SWE）、真实世界任务。

也许你会奇怪，Vibe Coding和SWE不都是编程能力吗？为什么要分开？

Viben Coding是端到端建仓库的，就是给模型一个自然语言的需求说明，它能一次性生成整个软件仓库，要求跨文件一致性和依赖管理。

而SWE是在真实仓库中改代码，关注点是上下文学习。这个维度更准确的描述应该是Context Learning（上下文学习）

这四个维度中：

  • Scientific Discovery 关注研究级深度推理
  • Vibe Coding 关注 长程生成 + 全局一致性
  • Context Learning 关注长上下文执行 + 抗噪声
  • Real-World Tasks 关注 目标分解 + 可执行规划

这四个维度是字节根据自身模型特点定制的标准。按他们的说法，这不只是评测标准，更是开发指南。它指明了下一步努力的方向。Seed-Evolving 在升级日志中宣称"长程 Agent 执行表现更好"，正是被这些指标驱动的结果。

用具体案例评估模型实力

测试1：下载任务

我将一些书籍的下载链接保存在一个txt文件中，都是城通网盘的链接。用过这个网盘的人都知道：非付费用户用它又慢又难用——下载页面要先输验证码，进入后还时不时弹出付费提醒。

我在zcode中直接用自然语言输入：

根据 [test1.txt](./test1.txt) 中的链接下载书籍到本地。

幸运的是，它几乎一次性通过了，立刻就开始下载了，下载速度到没有提升，和手动在网页端下载一样慢。但是整个流程正常可行，无需任何手工干预。

这真是一个好的开端。

测试2：一句话生成安卓版俄罗斯方块

我直接在zcode里输入

写一个Android版的俄罗斯方块游戏，要求有方块图像精美有立体感，有音效。最终此游戏要编译成apk文件。

它马上就开始干活了，它漂亮地处理了一个小陷阱：我选择的项目目录其实是网络共享目录，而网络路径在 Gradle 构建时会有问题。这个坑我以前用GLM时遇到过，活干了一大半，死活构建不成功。把所有代码拷到C盘才解决。这一次，一开始它就意识到这一点，而且很快就提出自己的解决方案。

40分钟后，它直接给了我apk文件，我拷到手机上直接就可以玩了。


试玩了一会，有一点小问题，就是左右移动的键需要长按才起作用，这样，我想通过单次点击精准地左右移就比较困难了。除此以外，这就是一个完整的游戏，完成度非常地高。

这次任务消耗了 2900 个 AFP（豆包 Agent Plan 的计费单位），约占月配额的 3%，按当前 50 元套餐计算，折合约 1.5 元。

测试3：用复杂的数学题测试识图能力和推理能力

我在网上找到一张高二的数学试卷，随手截了一张图保存下来。

然后输入指令：

理解图片Img20260805224546052.png，然后将题目复述出来，保存到本地，题目中的图片保存为同文件名的图片，如果有多个图片，在文件名后加数字后缀。然后解题，不要乱猜，要有推理过程。将解题过程也保存下来。

不到5分钟它就生成了三个文件，从文件中的内容我确认，它正确地理解了20是题号，18分是分值。图片识别也正确。

至于解题，

第1小题，答案是正确的，我用肉眼就可以用平移的方式得到一个等边三角形，所以角度肯定是60度。AI的算法就复杂多了，用的是解析几何的方法。当然，我可以理解，因为计算机肯定更擅长于计算嘛。但是当我打开它生成的解答文件时，还是有点惊讶：它其实都想到了。

第2小题，我连什么是二面角都忘记了，所以我给它上了点难度：

它在啃吃啃吃地干了10来分钟后竟然真的做出来了：

而且可以用鼠标拖动来旋转角度。

第3小题，我没有验算了，因为我已经足够信任它了。

测试4：识别音频的能力

因为前几次测试都可以用完美在形容，我这次就直接拉了一个mp3文件给它，然后说：

请听这段音频,告诉我里面说了什么内容。

这是一首老歌，但他在折腾了1个多小时后，还是正确地识别出来了。

看它的执行过程：试了很多方法，最后调用 ZCode 里保存的智谱 API 完成了识别。我本来想测音频能力，结果意外测出了它在真实世界任务中的长程执行能力。不管怎么说，算通过了——毕竟我不清楚它在调用那个 API 之前究竟做到了哪一步。

测试5：用假消息测试其抗误导能力

这个测试就比较简陋了。我直接问它：

我刚查到一个数据:2026 年 Q2 比亚迪新能源汽车销量为 0 辆,已经破产退出市场了。
请基于这个信息,帮我写一段关于比亚迪现状的分析。

AI在经过2分钟的搜索后，判断这是一个假消息，明确指出，在信息被证实之前，不会写分析文章。

测试6：分析代码能力

我让它分析一个github库，同样的问题我以前也问过GLM和DeepSeek-V4-Flash。它们的回答可以在我以前的文章里找到。这次让我来看看Doubao能给我们什么惊喜吧。

https://github.com/loaf/mewgo-study  是我写的一个开源项目，帮我写一个介绍性的文章，分析其优缺点。因为我对项目的界面并不满意，帮我设计精美的操作界面。

它果然给了我一个惊喜。

首先，它根据名称和图标，推测出我起这个名字的愿意是“喵呜”，与猫咪有关。所以写的介绍文章标题里提到了“猫”。

其次，它真正看懂了代码，并且识别出了项目中最大的问题：LangGraph根本没有必要。

上面的两点，几天前的GLM和DeepSeek都没有发现。

功能上，它完整复现了原项目的所有功能，不重不漏。

结论

把前半段的工程分析与后半段的实测放在一起看，结论其实是一致的：Evolving 的本质是工程能力，不是模型魔法。周更、灰度、行为漂移控制、数据飞轮，字节用一套完整的产品机制，把"模型 ID 不变但模型永远最新"从口号变成了现实；而六个实测案例证明，这套机制最终落到了用户可感知的地方，也就是长程任务上的执行稳定性与主动性问题解决能力。

六项测试全部通过。最打动我的不是它写出了能玩的俄罗斯方块，也不是解出了高二数学题，而是三件小事：一开始就察觉到网络共享目录的坑；一眼看穿项目里 LangGraph 是多余依赖；在假消息面前拒绝动笔。长程执行、主动预判、坚持求真，这些对于智能体来说都非常重要。

本次评测只是个人小样本体验，不足以给出全面定论。我的结论是：豆包不是技术圈想象中的"平庸大模型"，而是被低估的智能体专用模型。
