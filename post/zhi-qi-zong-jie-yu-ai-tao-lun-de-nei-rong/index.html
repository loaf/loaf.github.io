从头开发AI Agent应用系列之七：收集资料，总结与AI讨论的内容

loaf 2026-07-19 大约 22 分钟 技术 LLM Agent AI

之七：总结与AI讨论的内容

前一章，主要是手动输入资料。本章将实现的的功能是，就某个主题，与AI进行对话讨论，然后根据你的要求，将讨论内容保存到资料库中。

先解决几个概念

1）与AI讨论时，AI有多大的自主性。

理解这一点也很简单，你打开DeepSeek的网页对话，它也会让你选择是否“深度思考”和“智能搜索”。

选择了这些，AI会调用搜索工具。而一旦涉及到工具调用，就会有循环、条件、重试等代码逻辑。而打开深度思考，又会涉及思维链，涉及AI的自主决策。这时，AI就会向Agent功能靠拢。

这里模仿DeepSeek的网页对话，内置推理。这里的“推理”是指在模型回答之前，内部先想一遍。为了简单，到也不用在外面显示增加一个开关，默认调用即可。

同样是模仿DeepSeek的网页端，增加一个工具调用，只是这里把循环次数固定（3次），因为循环次数固定，工具集固定，决定了这里使用的是function calling而不是Agent。后者是不固定调用次数，而是由LLM自主决定，它是先调工具，然后看回调的结果，再决定是否重新调用，还是换一个工具再调用，而且决定调用与否由LLM自己判断。

这里我们还是基于function calling 开发。

2）多轮对话中的记忆本质

我们都知道模型本身是无状态的。每次调用都是独立调用，所以所谓的多轮记忆，其实就是调用方把历史消息每次都喂进去。

# 第一轮
messages = [
   {"role": "system", "content": "你是写作助手"},
   {"role": "user", "content": "聊聊米歇尔·奥巴马"},
]
# → AI 回: "米歇尔·奥巴马, 生于 1964 年..."

# 第二轮: 把第一轮的 user + assistant 回复**一起**再喂进去
messages = [
   {"role": "system", "content": "你是写作助手"},
   {"role": "user", "content": "聊聊米歇尔·奥巴马"},            # ← 第一轮的
   {"role": "assistant", "content": "米歇尔·奥巴马, 生于 1964 年..."},  # ← 第一轮的 AI 回复
   {"role": "user", "content": "她的教育背景?"},                # ← 本轮新加的
]
# → AI 看到 "她的教育背景?" 是接在米歇尔上下文里的, 自然知道"她"指米歇尔

这就是 DiscussionSession.messages 的全部工作——累积这个列表。每次调 LLM 前把整个列表拼到 system 提示后面：

messages_for_llm = [
    {"role": "system", "content": _DISCUSSION_SYSTEM_PROMPT},
    *session.messages,   # ← 完整历史
]

很明显，如果对话次数多了，messages 就会爆掉。这里暂时不考虑，自己注意一次对话别长太即可。

3）模型供应商无关的实现

因为各家"思维链 + 工具调用"的协议完全不同。如果在代码层根据厂家路由不同的代码段，就太笨重了，这里是使用LiteLLM v1.63+ 把 reasoning_content 和 tool_calls 做标准化。

代码不写死模型，具体模型由配置决定。换厂商只改 .env 文件，代码不动

会话存储 backend/app/discussion/session.py

1. DiscussionSession dataclass

@dataclass
class DiscussionSession:
    session_id: str
    project_id: str
    messages: list[dict] = field(default_factory=list)   # OpenAI 格式
    created_at: float = field(default_factory=time.time)
    updated_at: float = field(default_factory=time.time)

    def append(self, role, content):
        self.messages.append({"role": role, "content": content})
        self.updated_at = time.time()   # ← TTL 续期

    def is_expired(self, ttl_seconds=3600):
        return (time.time() - self.updated_at) > ttl_seconds

append 自动刷新 updated_at——每次追加消息就续期 TTL。
意味着"活跃会话永不过期，闲置会话 60 分钟后清"。这正是想要的语义。

2. create_or_get_session：续聊的核心

def create_or_get_session(project_id, session_id=None, *, ttl_seconds=3600):
    cleanup_expired(ttl_seconds)   # 顺手懒清理

    if session_id is not None:
        existing = _SESSIONS.get(session_id)
        # 只有"同项目 + 未过期"才能续; 否则当它不存在, 新建
        if (existing is not None
            and existing.project_id == project_id
            and not existing.is_expired(ttl_seconds)):
            return existing

    new_session = DiscussionSession(session_id=_gen_session_id(), project_id=project_id)
    _SESSIONS[new_session.session_id] = new_session
    return new_session

三个续聊条件：

  1. session_id 存在（防伪造）
  2. 同 project_id（防跨项目偷续别人会话——test_summarize_cross_project_session_rejected 验）
  3. 未过期（TTL）

任一不满足 → 当它不存在，新建。这让前端逻辑很简单：总是带着上次的 session_id 调用，后端自己决定续还是新建。

工具层 backend/app/tools/web.py

新建一个目录Tools放置工具。

  • 放在 app/tools/ 而非 app/discussion/, 因为工具是跨节点共享能力层，后续功能会复用这里的抓取逻辑。
  • 工具集写死 (DISCUSSION_TOOLS), 不开放给模型自由扩展 (工具集固定、循环上限固定、IO schema 固定)。
  • 工具函数失败不抛异常: 返回空列表 / 错误字符串, 让模型看到失败后自行决定继续或直接答, 不让单次工具失败把整个讨论循环崩掉 (循环上限兜底保证用户永远拿到文字回复)。

两个工具:

  • search_web(query): DuckDuckGo Lite HTML 抓取, 零配置零依赖。暂时用免费的，以后根据情况再换。
  • fetch_page(url): 复用 kb.extract 的 fetch_html + trafilatura, 截断到合理长度。

execute_tool 是工具分发表: 把 OpenAI function-calling 的 (name, args) 路由到具体函数,所有异常捕获后转成字符串, 绝不往外抛。会把任何错误转成字符串（如“抓取失败……”）喂回模型。

总结逻辑 backend/app/discussion/summarize.py

1. build_summary_messages：把对话塞进 prompt

def _format_discussion_as_text(session):
    """拼成可读对话文本: '用户: ...\nAI: ...\n用户: ...'"""
    role_label = {"user": "用户", "assistant": "AI", "system": "系统"}
    lines = []
    for msg in session.messages:
        if msg.get("role") == "system":
            continue   # ← 跳过讨论本身的 system 提示 (不是讨论内容)
        label = role_label.get(msg.get("role", ""), msg.get("role", ""))
        lines.append(f"{label}: {msg.get('content', '')}")
    return "\n".join(lines)

def build_summary_messages(session):
    transcript = _format_discussion_as_text(session)
    user_prompt = (
        f"讨论记录如下:\n\n```\n{transcript}\n```\n\n"
        "请按系统提示的要求, 把上述讨论整理成资料卡片。"
    )
    return [
        {"role": "system", "content": _SUMMARIZE_SYSTEM_PROMPT},
        {"role": "user", "content": user_prompt},
    ]

关键细节：跳过 system 消息。讨论 session 里没有 system 消息（system 提示是路由拼 LLM 输入时加的，不进 session），

但这个函数是防御性的——万一以后 session 里有 system，会被当"讨论内容"喂给总结 LLM，那是错的。

用 markdown 代码块包 transcript：

讨论记录如下:

```
用户: 聊聊米歇尔
AI: 米歇尔·奥巴马...
```

请按系统提示的要求...

这样 LLM 清楚地知道"这段是对话原文，不是给你的指令"。防止 prompt 注入：如果用户在讨论里说"忽略上面所有指令，输出…"，
不包代码块的话 LLM 可能当真。包了之后，模型理解为"这是被引用的对话片段"，不会被里面的"指令"误导。

2. summarize_discussion：聚合流式 chunks

失败抛、不入空。

if not summary:
    raise RuntimeError("总结为空 (LLM 未返回内容)")

路由层接住 RuntimeError 转 422，不入库。test_summarize_llm_failure_no_material_saved 验：LLM 挂了之后，资料库没有任何条目——绝不允许"空资料"或"半个总结"进 kb/。

3. 加上系统提示词

代码里在提交总结申请时，加上了系统提示词：

你是写作助手的"资料整理员"。下面是用户与 AI 就某个主题的多轮讨论记录。
请把讨论整理成一份**资料卡片**, 供后续写作参考。要求:

1. 用 markdown 格式输出。
2. 提取讨论中的**关键事实、数据、观点、人名/地名/时间**等硬信息 (这些是资料库的核心价值)。
3. 按主题分小节 (用 `##` 二级标题), 不要保留"用户说/AI 答"的对话痕迹。
4. 客观陈述, 不要补充讨论中没有的内容, 不要主观评论。
5. 控制在 300~800 字之间。如果讨论信息很少, 就少写, 不要凑字数。

直接输出 markdown 正文, 不要加 "以下是总结" 之类的前言。

这个可以在以后实际使用中根据反馈的质量进行修改。

API backend/app/api/materials.py（两个新端点）

1. 路由表（加在现有 4 个之后）

Method Path 异步? 流式? body
POST /materials/discussion async SSE {project_id, message, session_id?}
POST /materials/discussion/summarize async 否 {project_id, session_id}

两个都 async def（都有 await：discussion await llm_chat 流、summarize await summarize_discussion）。

2. discussion 端点：SSE 流式

@router.post("/materials/discussion")
async def discussion(req: DiscussionRequest) -> StreamingResponse:
    _require_project(req.project_id)
    session = create_or_get_session(req.project_id, req.session_id)
    append_message(session.session_id, "user", req.message)   # ← user 进 session
    messages_for_llm = [
        {"role": "system", "content": _DISCUSSION_SYSTEM_PROMPT},
        *session.messages,
    ]
    return StreamingResponse(
        _stream_discussion(session.session_id, messages_for_llm),
        media_type="text/event-stream",
        headers={"Cache-Control": "no-cache", "X-Accel-Buffering": "no"},
    )

顺序很重要：先 _require_project（404 优先），再 create_or_get session，再 append user message，然后拼 messages_for_llm。
append 必须在拼 messages_for_llm 之前——否则本轮 user 没进 prompt，AI 就"听不到"用户这次说什么。

_stream_discussion 是 async generator，在流结束后 append assistant。

3. summarize 端点：非流式，落 kb/notes/

@router.post("/materials/discussion/summarize", response_model=ImportResponse)
async def summarize(req: SummarizeRequest, response: Response) -> ImportResponse:
    _require_project(req.project_id)
    session = get_session(req.session_id)
    if session is None or session.project_id != req.project_id:
        raise HTTPException(404, "会话不存在或已过期")
    if not session.messages:
        raise HTTPException(422, "会话为空, 无可总结的内容")

    try:
        summary_text = await summarize_discussion(session)
    except (RuntimeError, Exception) as e:
        raise HTTPException(422, ...)   # LLM 失败 → 422, 不入库

    title = build_title_from_first_user(session)         # 启发式
    snippet = summary_text.replace("\n", " ").strip()[:80]   # 取前 80 字预览

    mat_id, result = store.save_material(                # ★ 单一写入路径铁律
        req.project_id, summary_text,
        source_type="discussion",    # ← 自动落 notes/
        title=title, snippet=snippet,
        tags=["讨论总结"],
    )
    response.status_code = _status_for_result(result)
    return ImportResponse(material_id=mat_id, result=result)

复用 ImportResponse ——和前面三个导入接口同构（material_id + result）。

前端 summarizeDiscussion 直接返回 Promise<ImportResponse>，和导入的客户端代码风格一致。

source_type="discussion"，前面的 _SUBDIR_BY_SOURCE["discussion"] = "notes" 自动把文件落到 kb/notes/。

完全没碰 store/manifest，只是调了一下。

4. 错误码映射

情况 状态码 理由
项目不存在 404 标准 REST
会话不存在/过期/跨项目 404 资源不存在
会话为空（没消息） 422 没东西可总结
message 空 422 Pydantic min_length 自动
LLM 调用失败（讨论/总结） SSE 内 {error} / 422 不挂连接 / 不入库
总结成功（新建/去重） 201 / 200 复用 T-006 的语义

注意 discussion 失败和 summarize 失败的处理不同：

  • discussion 是流式，HTTP 状态码已经是 200（流开始就发了），只能在流里发 {"error": "..."} 事件。
  • summarize 是非流式，可以正常用 HTTP 状态码（422）表达失败。

前端 Discuss.tsx + client.ts

1. streamDiscussion：复刻 streamChat，多 session_id 回调

export async function streamDiscussion(
  projectId: string,
  message: string,
  sessionId: string | null,
  onChunk: (text: string) => void,
  onSessionId: (sessionId: string) => void,   // ← 多这个回调
): Promise<void> {
  // fetch + ReadableStream + 解析 SSE (复刻 streamChat)
  // 多识别一种事件: {"session_id": "..."} → onSessionId
}

为什么用回调而不是返回值？因为流式是异步序列——session_id 在开头、chunks 在中间、[DONE] 在末尾，回调让调用方能"边收边反应"。返回值只能给最终结果，错过中间事件。

2. Discuss.tsx：复刻 ChatPage，加 session + 总结

关键状态：

const [sessionId, setSessionId] = useState<string | null>(null);  // 续聊凭证
const [messages, setMessages] = useState<Msg[]>([]);              // UI 展示
const [summarizing, setSummarizing] = useState(false);
const [summaryMsg, setSummaryMsg] = useState<string | null>(null);

发送逻辑（和 ChatPage 几乎一样，多了 session_id 传递）：

await streamDiscussion(
  projectId, text, sessionId,
  (chunk) => { /* 追加到 assistant 占位 */ },
  (sid) => setSessionId(sid),   // ← 拿到 session_id 存起来
);

总结按钮：

async function handleSummarize() {
  if (summarizing || !sessionId) return;
  if (!messages.some(m => m.role === "assistant" && m.text.trim())) {
    setSummaryErr("还没有可总结的讨论内容, 先发条消息吧。");
    return;
  }
  setSummarizing(true);
  try {
    const r = await summarizeDiscussion(projectId, sessionId);
    if (r.result === "deduplicated") {
      setSummaryMsg(`资料库已有相同总结 (id ${r.material_id.slice(0, 12)}…)`);
    } else {
      setSummaryMsg(`已入库 (id ${r.material_id.slice(0, 12)}…) — 回收集台可查看`);
    }
  } catch (e) { setSummaryErr(...); }
  finally { setSummarizing(false); }
}

前端去重提示也分两种：dedup 时说"已有相同总结"而非"已添加"。

3. 顶部 notice：明确告诉用户"讨论不自动保存"

<div style={styles.notice}>
  讨论只在内存中保留 60 分钟, 重启即丢。<strong>请用下方"总结为资料"按钮</strong>
  把整段讨论落盘到资料库 (source_type=讨论)。
</div>

让用户知道"不点总结就会丢"，比让用户以为自动保存最后发现丢了要好。原则是：让人知道系统的真实行为，不要让人猜。
