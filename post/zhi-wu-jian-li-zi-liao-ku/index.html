从头开发AI Agent应用系列之五：建一个写作资料库

loaf 2026-07-16 大约 12 分钟 技术 LLM Agent AI

之五：建立资料库

本章将为本应用建立一个资料库。这个资料库是一个简单的文件库。只是按来源分成不同的目录。

为什么不用RAG

考虑到实现的应用场景，对一个具体的主题而言（一篇文章）而言，资料肯定不需要太多，篇幅也不会太长，所以没有必要使用RAG来建一个向量数据库。

而且将文本向量化不仅消耗资源而且在搜索时，往往因为RAG的规则（比如选片大小，选片数量等），反而会丢资料，或者将资料内容割裂成碎片，无法形成因果关系。再加现代模型的长上下文，不如将文章直接喂给大模型。

所以这里的资料库直接调用文件系统。其物理结构为：

{workspace}/{project_id}/kb/
├── manifest.json          ← 索引文件（元数据列表）
├── pages/                 ← 抓取的网页 / URL 导入
│   ├── mat_xxx.md
│   └── mat_yyy.html
├── notes/                 ← 手写笔记 / 讨论总结 / 粘贴片段
│   └── mat_zzz.md
└── images/                ← 图片
    └── mat_www.png

正文是文件，manifest 只记元数据（标题、摘要、标签、路径、来源、哈希……）。

不过，对这个文件有点纠结。有的好处是巨大的，不光在搜索上起到很大作用，保存哈希值后，在去重方面会方便很多。而且以后还可以增加一个属性 ，保存文件的Token值， 这样可以在调用前预估调用成本，或者自动控制上下文长度（在超长时压缩）。代价是维护有点麻烦，你手工删除一个文件，或者用第三方应用修改文件，元数据没有办法实现更新。

因为资料库最终是以文件系统的形式保存在磁盘上的，所以没有办法控制外部应用或者其它人通过文件系统来操作文件。

但是在当前应用中，我们可以控制所有对文件的读写只通过本应用，不直接碰文件系统。也就是说，不支持向目录是拷贝一个文件的方式来增加资料，也不支持直接手工删除你认为无用的文件（你当然可以这么做，但会报错）。

Material 数据模型 backend/app/models/material.py

仍然是使用 Pydantic 库来建模。

SourceType = Literal["search", "discussion", "import", "note"]

class Material(BaseModel):
    id: str                          # mat_xxxxxxxxxxxx
    path: str                        # 相对 kb/ 的路径, 如 pages/mat_xxx.md

manifest 管理器 backend/app/kb/manifest.py

读：损坏时降级，不抛异常

def read_manifest(kb_root: Path) -> dict:
    path = kb_root / "manifest.json"
    if not path.exists():
        return _empty_manifest(project_id="")    # 不存在 → 空骨架
    try:
        data = json.loads(path.read_text(encoding="utf-8"))
    except (json.JSONDecodeError, OSError):
        corrupt = path.with_suffix(".json.corrupt")
        path.replace(corrupt)                     # 备份损坏文件
        return _empty_manifest(project_id="")    # 降级到空
    data.setdefault("materials", [])              # 防御性补字段
    return data

manifest 坏了不抛异常。如果抛，整个项目的所有资料操作都会挂掉，一个坏索引卡死整个资料库，代价过大。降级到空骨架意味着"当这个项目还没资料"， 后续 save 还能继续工作（重新写一份新 manifest），原数据丢了但至少不卡死。

而且坏文件不会直接被覆盖——先 rename 成 manifest.json.corrupt 备份， 用户/开发者还能从备份里捞数据。

原子写：.tmp + os.replace

def write_manifest(kb_root, manifest):
    path = kb_root / "manifest.json"
    tmp = path.with_suffix(".json.tmp")          # 1. 先写临时文件
    tmp.write_text(json.dumps(manifest, ...))
    os.replace(tmp, path)                        # 2. 原子替换

因为manifest 是关键索引文件，坏了全资料库就乱套。如果写系统写Manifest.json文件时崩溃，就会留下一个不完整的JSON文件，下次启动时，解析失败，整个项目的资料库都不可用了。所以先写临时文件，没问题后再替换。

[!TIP]
os.replace 在 POSIX 和 Windows 上都是原子 rename——操作系统保证这一步要么全成功要么全失败， 不会出现"manifest.json 被改成半个"。

一致性自检

前面说过，即使有单一写入路径，旁路操作仍可能发生：

  • 用户手动删了 kb/pages/mat_xxx.md（绕过 store）
  • 调试时直接往 kb/notes/ 丢个文件（绕过 store）
  • 程序 bug 写了一半崩了

这都有可能会导致元数据和真实资料不一致：

  • 悬空引用 (dangling_ref)：manifest 记了一条，但 path 指向的文件没了。
  • 孤儿文件 (orphan_file)：kb/ 下有文件，但 manifest 没记

check_consistency 把这两类都报出来：

def check_consistency(kb_root):
    manifest = read_manifest(kb_root)
    recorded = {m["path"]: m for m in manifest["materials"] if m.get("path")}
    actual = {扫 pages/notes/images 下所有文件的相对路径}

    dangling = [m for path, m in recorded.items() if path not in actual]
    orphan = sorted(p for p in actual if p not in recorded)
    return ConsistencyReport(dangling_refs=dangling, orphan_files=orphan)

返回的是一个数据类 ConsistencyReport：

@dataclass
class ConsistencyReport:
    dangling_refs: list[dict]    # 悬空引用 (manifest 有, 文件没)
    orphan_files: list[str]      # 孤儿文件 (文件有, manifest 没)

    @property
    def is_clean(self) -> bool:
        return not self.dangling_refs and not self.orphan_files

对外读写层 kb/store.py

这是操作文件的唯一入口。

save_material：去重 → 写文件 → 登记 manifest

def save_material(project_id, content, *, source_type, title="", ...) -> tuple[str, SaveResult]:
    kb = kb_dir(project_id)
    # 1. 兜底建目录 (T-004 已建, 这里 exist_ok 防御)
    kb.mkdir(parents=True, exist_ok=True)
    for sub in ("pages", "notes", "images"):
        (kb / sub).mkdir(exist_ok=True)

    content_hash = compute_content_hash(content)

    # 2. 去重: 命中已存在就直接返回
    mf = read_manifest(kb)
    existing = find_by_hash(mf, content_hash)
    if existing is not None:
        return existing["id"], "deduplicated"

    # 3. 写文件 (按 source_type 路由到子目录)
    subdir = _SUBDIR_BY_SOURCE.get(source_type, "notes")
    name = (filename or _gen_material_id()) + _TEXT_EXT
    rel_path = f"{subdir}/{name}"
    (kb / rel_path).write_text(content, encoding="utf-8")

    # 4. 登记 manifest (原子写)
    material = Material(id=_gen_material_id(), path=rel_path, ...)
    append_material(kb, material)
    return material.id, "created"

source_type → 子目录的路由

_SUBDIR_BY_SOURCE = {
    "search": "pages",        # 抓回的网页
    "import": "pages",        # URL 抓取 / 文件导入
    "discussion": "notes",    # 讨论总结
    "note": "notes",          # 手写 / 粘贴
}

delete_material：先删 manifest，再删文件

def delete_material(project_id, material_id) -> bool:
    kb = kb_dir(project_id)
    removed = remove_material_by_id(kb, material_id)    # 1. 先从 manifest 移除
    if removed is None:
        return False                                     # 没找到, 返回 False 不报错
    file_path = kb / removed.get("path", "")
    try:
        if file_path.is_file():
            file_path.unlink()                           # 2. 再删磁盘文件
    except OSError:
        pass                                             # 文件删不掉不回滚 manifest
    return True

之所以先删manifest，再删文件，是因为一个原则 ：悬空引用比孤儿文件更糟糕。

最后

这一章比较简单，重点在于数据的一致性，其实如果再简单一点的话，连manifest都可以不要，只建一个文件目录即可。这里之所以过度设计，是因为我还想以后将这个资料库扩展成一个能相互引用的网状资料库，但又不想使用数据库，只能想办法先熟悉一下将文件元数据保存在当前目录下的方法。

现在代码部分只是选择性地贴了一部分。实际代码要多的多。项目最终完成后，会将代码上传到github。
